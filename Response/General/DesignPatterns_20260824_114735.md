### 🔹 1. **Orchestrator / Workflow Pattern** (Replaces God Objects)
**Where it fits:** `SummaryAgent`, `EmbeddingPipeline`
**Why:** `SummaryAgent` currently handles directory I/O, prompt assembly, LLM invocation, retry logic, and cancellation. This violates SRP and makes testing/mocking difficult.

**Recommendation:** Extract coordination into a dedicated orchestrator that composes discrete steps:
```csharp
public interface IQuestionAnsweringOrchestrator
{
    Task<AnswerResult> ExecuteAsync(string folderPath, string question, CancellationToken ct);
}

// Composition root
var orchestrator = new QuestionAnsweringOrchestrator(
    fileLoader: new DirectoryFileLoader(),
    evidenceRetriever: new VectorStoreEvidenceRetriever(qdrantClient),
    agentInvoker: new OllamaAgentInvoker(clientFactory),
    responseFormatter: new MarkdownResponseWriter(config)
);
```
**Benefit:** Each step is independently testable, swappable (e.g., swap LLM provider), and retry/logging can be applied per-step without polluting business logic.

### 🔹 2. **Builder Pattern** (For Complex DTOs & AI Requests)
**Where it fits:** `SaveDetails`, `GenerateRequest`, `QuestionConfiguration`
**Why:** Your tests manually construct objects with multiple parameters (`new SaveDetails(question, "Generated Answer", "00:15")`). As fields grow, constructors become fragile and unreadable.

**Recommendation:** Introduce builders for fluent construction & test setup:
```csharp
public class SaveDetailsBuilder
{
    private string _category = "Uncategorized";
    public SaveDetailsBuilder WithCategory(string cat) { _category = cat; return this; }
    public SaveDetails Build() => new(_question, _response, _duration, _category);
}

// Usage in tests:
var details = new SaveDetailsBuilder()
    .WithQuestion(testQ)
    .WithResponse("AI generated answer")
    .WithDuration("00:15")
    .Build();
```
**Benefit:** Eliminates constructor parameter bloat, enables optional fields, and dramatically cleans up test fixtures.

### 🔹 3. **Result Pattern** (For Expected Control Flow)
**Where it fits:** `LoadQuestionAsync`, `ExpandDirectory`, LLM calls
**Why:** You're using exceptions (`DirectoryNotFoundException`, `ArgumentException`) for expected scenarios (missing dirs, invalid CSV rows). Exceptions are expensive and break async flow composition.

**Recommendation:** Replace exception-driven control flow with `Result<T>` or `Option<T>`:
```csharp
public static Result<string> ExpandDirectory(string path)
{
    if (string.IsNullOrWhiteSpace(path)) return Result.Fail("Path is null or empty");
    
    var expanded = Environment.ExpandEnvironmentVariables(path);
    var fullPath = Path.GetFullPath(expanded);
    return Directory.Exists(fullPath) 
        ? Result.Ok(fullPath) 
        : Result.Fail<string>($"Directory not found: '{fullPath}'");
}

// Usage:
var dirResult = path.ExpandDirectory();
if (dirResult.IsSuccess) { /* proceed */ }
else { logger.Warning(dirResult.Error); }
```
**Benefit:** Makes error paths explicit, composable (`dirResult.Then(ProcessFile)`), and vastly improves testability without mocking `Assert.Throws`.

### 🔹 4. **Pipeline / Chain of Responsibility Pattern** (For File Parsing)
**Where it fits:** `FileParseFactory`, `XmlCommentFilterStrategy`, CSV loading
**Why:** Parsing likely involves multiple transformation steps: read → strip XML comments → extract metadata → format for embedding. Currently, filtering is a separate strategy but not chained.

**Recommendation:** Define a processing pipeline where each step can pass or reject the record:
```csharp
public interface IParseStep
{
    Task<PipelineResult> ProcessAsync(ParseContext context, CancellationToken ct);
}

// Pipeline composition
var steps = new List<IParseStep>
{
    new XmlCommentFilterStrategy(),
    new MetadataExtractorStep(),
    new EmbeddingFormatStep()
};

public async Task<IEnumerable<QuestionConfiguration>> LoadQuestionsAsync(CancellationToken ct)
{
    var pipeline = new ParsePipeline(steps);
    return await pipeline.ExecuteAsync(csvStream, ct);
}
```
**Benefit:** Steps are independently testable, order can be configured per file type, and filtering logic stays decoupled from I/O.

### 🔹 5. **Decorator Pattern** (For Cross-Cutting Concerns)
**Where it fits:** LLM clients, file readers, async operations
**Why:** Retry (`Polly`), timing (`StopwatchExtensions`), logging, and cancellation are currently inline or scattered as extensions. This couples infrastructure to business logic.

**Recommendation:** Wrap core services with decorators:
```csharp
// Core interface
public interface IEmbeddingService { Task<ReadOnlyMemory<float>> GenerateAsync(string input, CancellationToken ct); }

// Decorator
public class RetryLoggingEmbeddingDecorator : IEmbeddingService
{
    private readonly IEmbeddingService _inner;
    private readonly ILogger _logger;
    public async Task<ReadOnlyMemory<float>> GenerateAsync(string input, CancellationToken ct)
    {
        using var sw = Stopwatch.StartNew();
        return await Policy.Handle<HttpRequestException>()
            .WaitAndRetryAsync(3, r => TimeSpan.FromSeconds(Math.Pow(2, r)))
            .ExecuteAsync(async () => 
            {
                _logger.LogDebug("Calling embedding service...");
                var result = await _inner.GenerateAsync(input, ct);
                _logger.LogDebug($"Embedding completed in {sw.ElapsedMilliseconds}ms");
                return result;
            });
    }
}

// DI Registration
builder.Services.Decorate<IEmbeddingService, RetryLoggingEmbeddingDecorator>();
```
**Benefit:** Keeps `OllamaEmbeddingService` pure. Cross-cutting concerns are applied declaratively in composition root.
