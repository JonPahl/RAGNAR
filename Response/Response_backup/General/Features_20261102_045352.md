## Recommended Feature: Retrieval Transparency & Source Attribution

After reviewing the architecture, the highest-impact addition I'd recommend is a **retrieval explainability layer** that surfaces *which* code segments were retrieved, *where* they came from, and *how relevant* they scored — rendered before (or alongside) the generated answer.

### Why This Matters

The pipeline currently flows:

```
Question → Embed → Qdrant Search → Context Text → LLM → Answer
```

The `contextText` passed into `RagOrchestrator.ExecuteAsync` is an opaque blob. The Qdrant search response carries rich metadata (file path, line range, similarity score, payload fields like `Category` and `CommentLength` — all visible in `QdrantFilterBuilder` and `CodeDocument`), but none of it reaches the user. For a *code-focused* RAG tool, that's a significant trust and debug gap.

### What It Would Look Like

A new pipeline stage (or a decorator on the retrieval stage) that, after the Qdrant query completes, renders a structured "evidence panel" to the console using the existing `ITableRenderer` / `NumberedRowDecorator` infrastructure:

| # | File | Lines | Score | Category | Excerpt |
|---|------|-------|-------|----------|---------|
| 1 | `PaymentService.cs` | 45–62 | 0.91 | Production | `public async Task<PaymentResult> …` |
| 2 | `OrderHandler.cs` | 12–30 | 0.84 | Production | `void OnOrderCreated(Order o) …` |
| 3 | `TestHelpers.cs` | 80–95 | 0.72 | Tests | `public static Order CreateSample…` |

Then, in the saved response file, a fenced section (reusing `ShowPrompt()` / `PromptFormatting.Fence`) records the same table so the user can audit *why* the LLM answered the way it did.

### Where It Fits in the Existing Architecture

| Existing piece | How it connects |
|---|---|
| `QdrantFilterBuilder` / `QuestionFilterSelector` | Already builds the `Filter`; the search call returns scored hits — the new stage just *reads* that response instead of flattening it to a string. |
| `PipelineRunner<TContext>` + `StageExecutionContext<TContext>` | Add a `RetrievalEvidence` list to `QuestionPipelineContext` (alongside the existing `Responses` and `Timings` dictionaries). A new `IReadOnlyList<RetrievalHit> Hits` property is all that's needed. |
| `StageTimingMiddleware` | Already wraps every stage; the evidence-rendering stage gets its own timing for free. |
| `NumberedRowDecorator` / `ITableRenderer` | Render the evidence table with zero new rendering code. |
| `OutputPathHelper.GetResponseDirectory` / `IResponseWriter` | Append the evidence table to the saved `.md` response file. |
| `configWrapper.Value.ApplicationOptions` | Add an `IncludeRetrievalEvidence: bool` flag (default `true`), mirroring the existing `IncludeOriginalPrompt` toggle. |

### Why Not the Obvious Alternatives?

- **Streaming tokens**: Nice UX win, but it changes the I/O contract of `IOllamaGenerationService` and `RagOrchestrator` and is more invasive for a CLI tool where the full answer is saved to disk anyway.
- **Conversation history / multi-turn**: Powerful, but the current design is batch-oriented (load N questions → answer each). Adding a session layer is a larger architectural shift.
- **Reranking (e.g., a cross-encoder pass)**: Valuable for quality, but it adds a second Ollama call per question, doubling latency and GPU load. Evidence transparency delivers 80 % of the debugging value for 5 % of the cost.

### Effort Estimate

- `RetrievalHit` record + context property: **~15 min**
- `RetrievalEvidenceStage` + table rendering: **~1 h**
- Persisting evidence into the saved response (extend `ResponseRecord`): **~30 min**
- Config flag + unit test: **~30 min**

Roughly **two focused sessions** to ship, reusing virtually every existing abstraction (pipeline, middleware, DI, table rendering, config, output writer) with no new external dependencies.
