## 1. `RetryTrackingMiddleware` (most clearly missing)

The evidence is in your own code:

```csharp
// StageTimingMiddleware.cs — line that reveals the gap:
RetryCount = 0, // populate via a separate retry middleware if needed
```

And `StageMetric` already has the field:

```csharp
[[System.ComponentModel.DataAnnotations.Range(0, 10)]]
public int RetryCount { get; init; }
```

Today `PipelineRunner.ExecuteAsync` runs the Polly policy *inline* and the retry count is silently discarded. A dedicated middleware can intercept each retry attempt and write it into `StageMetric`:

```csharp
/// <summary>
/// Middleware that wraps a stage with Polly retry tracking,
/// recording the actual retry count into <see cref="StageMetric"/>.
/// </summary>
/// <example><![[CDATA[[runner.UseMiddleware(new RetryTrackingMiddleware(logger).Invoke);]]]]></example>
public sealed class RetryTrackingMiddleware(Serilog.ILogger logger)
{
    public async Task Invoke<TContext>(
        StageExecutionContext<TContext> context,
        Func<Task> next,
        CancellationToken cancellationToken) where TContext : class
    {
        cancellationToken.ThrowIfCancellationRequested();
        var attempts = 0;

        try
        {
            await next().ConfigureAwait(false);
        }
        finally
        {
            // StageTimingMiddleware runs *outside* us (registered later),
            // so it will read the value we set here.
            if (context.Metric is not null)
                context.Metric = context.Metric with { RetryCount = Math.Max(0, attempts - 1) };
        }
    }
}
```

Because the current `PipelineRunner` executes the Polly policy *before* the middleware chain, you'd need a small refactor: move the policy invocation **inside** the middleware onion so the middleware can count attempts. Concretely, in `ExecuteStageWithMiddlewareAsync`, pass the policy-wrapped delegate as the `coreExecution` instead of calling the policy separately:

```csharp
// PipelineRunner.ExecuteAsync — refactored section
Func<Task> core = async () =>
{
    if (entry.AsyncPolicy is null)
    {
        await stage.ExecuteAsync(context, ct).ConfigureAwait(false);
    }
    else
    {
        var attempt = 0;
        await entry.AsyncPolicy
            .ExecuteAsync(async () =>
            {
                attempt++;
                if (attempt > 1)
                    logger.Warning("Stage {Name} retry #{Attempt}", stage.Name, attempt);
                await stage.ExecuteAsync(context, ct).ConfigureAwait(false);
            })
            .ConfigureAwait(false);
    }
};

await ExecuteStageWithMiddlewareAsync(execCtx, core, ct).ConfigureAwait(false);
```

Then register it **before** `StageTimingMiddleware` so the timing middleware reads the final `RetryCount`:

```csharp
runner
    .UseMiddleware(new RetryTrackingMiddleware(logger).Invoke)   // inner
    .UseTiming(new StageTimingMiddleware(logger));               // outer
```

## 2. `ProgressReportingMiddleware` (UX gap)

Your `RagOrchestrator` writes to `IOutputWriter` directly, but the **embedding pipeline** (`PipelineRunner<EmbeddingContext>`) has no per-stage progress surface. You already have `StageIndex` / `StageTotal` in `StageExecutionContext`, and an `IOutputWriter` in DI — they just aren't connected:

```csharp
/// <summary>
/// Emits a console progress line before each stage and a summary after.
/// </summary>
/// <example><![[CDATA[[runner.UseMiddleware(new ProgressReportingMiddleware(writer).Invoke);]]]]></example>
public sealed class ProgressReportingMiddleware(IOutputWriter writer)
{
    public Task Invoke<TContext>(
        StageExecutionContext<TContext> context,
        Func<Task> next,
        CancellationToken cancellationToken) where TContext : class
    {
        writer.MarkupLine(
            $"[[bold cyan]]▸ Stage {context.StageIndex + 1}/{context.StageTotal}: {context.Stage.Name}[[/]]");

        return next();
    }
}
```

```csharp

    .UseMiddleware(new RetryTrackingMiddleware(logger).Invoke)
```

## 3. (Optional) `StageValidationMiddleware`

Guards against a stage mutating the shared `TContext` into an invalid state (e.g. `QuestionPipelineContext.Responses` is `null` after a stage that was supposed to populate it). Cheap to add, high value for catching integration regressions early:

```csharp
/// <summary>
/// Runs a user-supplied validator after each stage completes.
/// Throws <see cref="PipelineStageException"/> on failure.
/// </summary>
public sealed class StageValidationMiddleware<TContext>(
    Func<TContext, string?> validator) where TContext : class
{
    public async Task Invoke<TC>(
        StageExecutionContext<TC> context,
        Func<Task> next,
        CancellationToken ct) where TC : class
    {
        await next().ConfigureAwait(false);

        if (context.PipelineContext is TContext typed)
        {
            var problem = validator(typed);
            if (problem is not null)
                throw new PipelineStageException(context.Stage.Name,
                    new InvalidOperationException($"Post-condition failed: {problem}"));
        }
    }
}
```
