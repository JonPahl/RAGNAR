## 1. `PipelineRunner.ExecuteAsync` Silently Bypasses the Entire Middleware Chain

**Impact: Critical (Silent Functional Defect)** | **Remediation: Medium**

This is the most severe issue in the codebase because it *appears* to work but does not. The `ExecuteAsync` method constructs a `StageExecutionContext` and a `core` delegate, then **directly invokes** `stage.ExecuteAsync` (with or without Polly policy) — never calling `ExecuteStageWithMiddlewareAsync`:

```csharp
// PipelineRunner.cs — ExecuteAsync
var execCtx = new StageExecutionContext<TContext>(stage, context, i, snapshot.Count);
Func<Task> core = async () =>
{
    if (entry.AsyncPolicy is null)
        await stage.ExecuteAsync(context, ct).ConfigureAwait(false);
    else
        await entry.AsyncPolicy.ExecuteAsync(async () => await stage.ExecuteAsync(context, ct).ConfigureAwait(false)).ConfigureAwait(false);
};

// ⚠️ 'core' and 'execCtx' are never used. Execution falls through to:
try
{
    if (snapshot[[i]].AsyncPolicy is null)
        await stage.ExecuteAsync(context, ct).ConfigureAwait(false);   // ← direct call
    else
        await snapshot[[i]].AsyncPolicy.ExecuteAsync(async () => await stage.ExecuteAsync(context, ct).ConfigureAwait(false)).ConfigureAwait(false);
}
```

**Consequences:**
- `StageTimingMiddleware` (and any future middleware) is **never invoked**. `StageMetric` is never populated.
- The onion-wrapping logic in `ExecuteStageWithMiddlewareAsync` is dead code.
- Observability (per-stage timing, success/failure flags, retry counts) is entirely absent at runtime.
- Any middleware added via `UseMiddleware(...)` or `UseTiming(...)` has **zero effect**.

**Remediation (~30 min + tests):**
Replace the duplicated direct-execution block with a single call:

```csharp
var execCtx = new StageExecutionContext<TContext>(stage, context, i, snapshot.Count);
Func<Task> core = async () =>
{
    if (entry.AsyncPolicy is null)
        await stage.ExecuteAsync(context, ct).ConfigureAwait(false);
    else
        await entry.AsyncPolicy.ExecuteAsync(
            () => stage.ExecuteAsync(context, ct)).ConfigureAwait(false);
};

await ExecuteStageWithMiddlewareAsync(execCtx, core, ct).ConfigureAwait(false);
```

Delete the redundant `try/catch` that duplicates the policy logic (the middleware chain already handles wrapping). Add an integration test that registers `StageTimingMiddleware` and asserts `context.Metric` is non-null after execution.

## 2. `RagOrchestrator` Discards All `GenerationOptions` at Inference Time

**Impact: High (Unbounded Cost + Non-Deterministic Output)** | **Remediation: Low**

`GenerationOptions` is a fully validated record with `MaxTokens`, `Temperature`, `RepeatPenalty`, `ContextWindow`, and `ThreadCount`. Yet `RagOrchestrator.ExecuteAsync` constructs the request with **only** `Model`, `Prompt`, and `System`:

```csharp
var request = new GenerateRequest
{
    Model  = ollamaClient.SelectedModel,
    Prompt = finalPrompt,
    System = promptTemplateProvider.System,
    // MaxTokens   ← missing
    // Temperature ← missing
    // RepeatPenalty ← missing
    // Options     ← missing (or equivalent field)
};
```

**Consequences:**
- **Unbounded generation**: Without `MaxTokens`, Ollama will generate until it hits its own internal cap (often 128K+), inflating latency and cost per query.
- **Non-deterministic answers**: Default temperature (often 0.7) produces different answers on repeated runs, making RAG evaluation impossible.
- **Repetition loops**: No `RepeatPenalty` means the model can cycle, wasting tokens.
- The entire `GenerationOptions` record, its `Range`/`DataAnnotations` validation, and the `FluentValidation` rules around it are **dead configuration**.

**Remediation (~15 min):**
Inject `IOptions<GenerationOptions>` (or read from the existing `configWrapper`) and map:

```csharp
var genOpts = configWrapper.Value.GenerationOptions; // or a dedicated IOptions<GenerationOptions>
var request = new GenerateRequest
{
    Model         = ollamaClient.SelectedModel,
    Prompt        = finalPrompt,
    System        = promptTemplateProvider.System,
    Options       = new OllamaOptions
    {
        MaxTokens      = genOpts.MaxTokens,
        Temperature    = genOpts.Temperature,
        RepeatPenalty  = genOpts.RepeatPenalty,
    },
};
```

Wire `GenerationOptions` into the DI registration and `appsettings.json` if not already done.

## 3. `QuestionFilterSelector.FindFilter` Mutates Internal State on Every Query Call

**Impact: Medium (Correctness + DI Contract Violation)** | **Remediation: Low**

```csharp
public Filter FindFilter(QuestionCategory category, int commentLengthThreshold = 0)
{
    // ⚠️ Mutation during a read/query operation
    _strategies.TryAdd(QuestionCategory.XML, new XmlCommentFilterStrategy(logger));

    var filter = _strategies.TryGetValue(category, out var strategy)
        ? strategy.CreateFilter(commentLengthThreshold)
        : new Filter();
    return filter;
}
```

**Consequences:**
- **Inconsistent state**: If the XML strategy was *not* passed via the constructor's `strategies` enumerable, it is lazily injected on the **first** `FindFilter` call. Before that call, `_strategies` lacks the entry and any code inspecting the dictionary sees a different set of keys than after.
- **Silent failure for other categories**: If a new `QuestionCategory` is added but no strategy is registered in DI, `FindFilter` returns an **empty `Filter`** (no `Must`, no `MustNot`) rather than surfacing a configuration error. The pipeline proceeds with unfiltered queries, returning irrelevant vectors.
- **Bypasses DI**: The strategy is constructed with a raw `logger` reference, not resolved from the container. If `XmlCommentFilterStrategy` later needs additional dependencies, this path breaks.
- Violates the **Single Responsibility** and **Open/Closed** principles — the query method has a side effect on the registry.

**Remediation (~20 min):**
1. Remove the `TryAdd` line from `FindFilter`.
2. Register `XmlCommentFilterStrategy` (and any other category strategies) in `EmbeddingSetupExtension`:

```csharp
services.AddSingleton<IFilterStrategy, XmlCommentFilterStrategy>();
// Add more as categories are introduced
```

3. Replace the silent `new Filter()` fallback with an explicit failure:

```csharp
if (!_strategies.TryGetValue(category, out var strategy))
    throw new NotSupportedException(
        $"No IFilterStrategy registered for category '{category}'. " +
        $"Register one in EmbeddingSetupExtension.");

return strategy.CreateFilter(commentLengthThreshold);
```

4. Add a unit test asserting that querying an unregistered category throws rather than returning an empty filter.
