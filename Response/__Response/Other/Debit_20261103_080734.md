# Technical Debt Assessment — Ragnar C# Application

Below is a prioritized catalogue of technical debt I can identify from the provided source. I've grouped findings by severity and category.

---

## 🔴 High-Impact (Likely to cause bugs or build breakage)

### 1. Duplicate `EmbeddingSetupExtension` registration
The file `EmbeddingSetupExtension.cs` is provided **twice** — once as a file-scoped `extension(IServiceCollection services)` block and once as a `static class EmbeddingSetupExtension`. Both register the same five singletons. Whichever compiles will conflict at DI registration time (duplicate `AddSingleton` calls) or at compile time (duplicate extension method). This is either a copy-paste artifact that slipped into the repo or a merge conflict that wasn't resolved.

### 2. Dead commented-out block in `PipelineRunner.ExecuteAsync`
```csharp
//try {
//    if (snapshot[[i]].AsyncPolicy is null) { ... }
//    else { ... }
//}
//catch (OperationCanceledException) when (ct.IsCancellationRequested) { throw; }
//catch (Exception ex) { ... }
```
This is the *original* implementation sitting directly below the rewritten one. It will confuse future maintainers, obscure the actual control flow, and the commented block references `snapshot[[i]]` while the live code uses `entry` — a subtle rename that the dead code doesn't reflect.

### 3. `QuestionFilterSelector` mutates a "readonly" dictionary
```csharp
private readonly Dictionary<QuestionCategory, IFilterStrategy> _strategies;
```
The field is assigned via `strategies.ToDictionary(...)` in the constructor, then **conditionally mutated** with `_strategies[[QuestionCategory.XML]] = new XmlCommentFilterStrategy(logger)`. The `readonly` modifier prevents reassignment but not mutation. More importantly, the built-in XML strategy is registered *after* the DI-injected strategies, meaning it can silently override a DI-registered strategy with the same key. The intent is ambiguous: is it a fallback or a forced override?

### 4. `StageExecutionContext` is a `record` with a mutable property
```csharp
public sealed record StageExecutionContext<TContext>(...)
{
    public StageMetric? Metric { get; set; }   // ← mutable
}
```
Records imply value semantics and immutability. Having a `set`-backed property that middleware mutates in place breaks that contract and makes the type behave like a plain POCO while still inheriting record `==`, `Equals`, and `ToString` (which will include `Metric` and produce inconsistent results before/after mutation).

## 🟠 Medium-Impact (Design smells that will compound)

### 5. `QdrantFilterBuilder` has dead members
| Member | Problem |
|---|---|
| `private readonly List<Condition> _should = [[]];` | Never populated by any public method. Always empty in `Build()`. |
| `private static Condition CloneCondition(Condition c) => c.Clone();` | Never called anywhere in the file. |

Both are YAGNI violations that suggest a half-finished feature was committed.

### 6. `CodeParserFactory` instantiates parsers directly
```csharp
private readonly ParseCSharpFile _codeParser = new(logger, cSharpFile);
private readonly MarkdownFileParser _markdownParser = new(options, logger);
```
These concrete types are `new`-ed inside the factory rather than injected via constructor. This makes the factory **untestable in isolation** — you can't substitute a stub `IFileParser` without a real file on disk. Compare with the rest of the codebase which consistently uses DI.

### 7. `IFileParser` violates single-responsibility
```csharp
Task<IEnumerable<CodeDocument>> ParseAsync(string filePath, CancellationToken ct);
Task<string> ReadFileAsync(string filePath, CancellationToken ct);   // ← unrelated
```
Reading raw file text has nothing to do with parsing into embeddable segments. Any consumer that only needs the content still has to depend on the full parser contract.

### 8. `RagOrchestrator` swallows generation failure then unconditionally saves
```csharp
catch (Exception ex) when (ex is not OperationCanceledException)
{
    response = "⚠️  Generation failed. Check the Ollama service and retry.";
}
// …falls through…
await SaveResponseAsync(new ResponseRecord(question, response, sw.FormatElapsedTime()), ct);
```
The error message string is persisted as if it were a real answer, and `SaveResponseAsync` itself has no guard against writing a known-failure sentinel to disk. Downstream consumers reading the response files cannot distinguish a valid answer from an error placeholder without string-matching.

### 9. `FileDiscoveryService` uses `await Task.Yield()` inside a synchronous `foreach`
```csharp
foreach (var path in Directory.EnumerateFiles(directory, "*.*", SearchOption.AllDirectories))
{
    // …
    yield return path;
    await Task.Yield();   // ← forces a context switch per file
}
```
`Directory.EnumerateFiles` is already lazy/synchronous. The `Task.Yield()` adds an unnecessary thread-pool round-trip for every single file, which will measurably slow down large directory trees. If the goal is to allow cancellation between files, `cancellationToken.ThrowIfCancellationRequested()` (already present) is sufficient.

### 10. `EmbeddingOptions.Host` is typed `Uri`
```csharp
public required Uri Host { get; init; }
```
Configuration binding from `appsettings.json` or environment variables expects a `string`. Requiring a `Uri` at the model level forces the host to be a valid URI *at parse time*, which means `"localhost"` (without a scheme) will **fail validation** in most binding scenarios. A `string` or `Uri?` with a separate validation step would be more ergonomic.

### 11. `NumberedRowDecorator` has a stateful `_numbered` guard and O(n²) row manipulation
```csharp
private bool _numbered;
public void Render()
{
    if (_numbered) { inner.Render(); return; }
    _numbered = true;
    // … clears and re-adds every row …
}
```
Two issues: (a) the boolean flag makes the object **non-reusable** and its correctness depends on call-order rather than type safety; (b) the loop calls `table.AddRow(row)` for each pre-existing row, but the rows were already present, so you end up with **duplicated rows** unless `AddRow` replaces (which the comment `// ← replace, don't add` hints at, but the code doesn't do).

## 🟡 Lower-Impact (Maintainability / Consistency)

### 12. Inconsistent `extension` vs `static class` pattern
- `AssemblyExtensions` uses C# 14 file-scoped `extension(Assembly asm)`.
- `EmbeddingSetupExtension` is a `static class` that *contains* an `extension` block.
- `QuestionsExtensions` is a `static class` with an `extension` block inside.
- `OutputPathHelper` is a plain `static class` with `this` modifiers.

All four accomplish the same thing. Picking one convention (e.g., file-scoped `extension` since the project is already on a modern C# version) would reduce cognitive load.

### 13. `RagOrchestrator` accepts 8 constructor parameters
```csharp
public sealed class RagOrchestrator(
    Serilog.ILogger logger,
    IOutputWriter writer,
    IOptions<RagnarConfig> configWrapper,
    IChatPromptProvider promptTemplateProvider,
    IRagPromptBuilder promptBuilder,
    IResponseWriter saveService,
    IOllamaClientFactory ollamaClientFactory,
    IOllamaGenerationService ollamaProvider)
```
Eight dependencies in a primary constructor is a strong smell that the class is doing too much: prompt building, client resolution, generation, persistence, and console output. Splitting into a `RagGenerator` (prompt + LLM call) and a `RagPersistenceService` (save + console) would make each unit independently testable.

### 14. `BrandingStage.ExecuteAsync` ignores its `CancellationToken`
```csharp
public Task ExecuteAsync(EmbeddingContext context, CancellationToken cancellationToken)
{
    header.RenderBranding();
    return Task.CompletedTask;
}
```
The token is accepted but never checked. If `RenderBranding()` ever becomes I/O-bound (e.g., reading a logo from disk), the cancellation contract is silently violated.

### 15. Missing validation in `RagOrchestrator.ExecuteAsync`
`question.Text` is used directly in the prompt and in the error log but is never null/empty-checked. A `Guard.Against.Null(question)` / `Guard.Against.NullOrEmpty(question.Text)` at the top of the method is absent.

### 16. `PipelineRunner` locks a `List<T>` but exposes `StageNames` with a second lock
The lock discipline is correct but the API surface (`AddStage`, `RemoveStage`, `Reorder`, `ReplaceStage`, `ClearStages`, `StageNames`) suggests a collection-like object. A dedicated `StageCollection<T>` with its own locking would separate the thread-safety concern from the execution concern and make the runner's code dramatically shorter.

### 17. `GenerationOptions` lives outside `RagnarConfig` validation chain
`RagnarConfigValidator` composes validators for `EmbeddingOptions`, `OllamaOptions`, and `FileLoadOptions`, but `GenerationOptions` (which has `[[Range]]` attributes on `MaxTokens`, `Temperature`, etc.) is validated only via data-annotation attributes that require a separate `Validator` call or `TryValidateObject`. There's no explicit `SetValidator` for it in the composition root.

### 18. XML doc comments are duplicated outside and inside type declarations
Multiple files (e.g., `EmbeddingSetupExtension.cs`, `AssemblyExtensions.cs`) repeat the same `<summary>` / `<example>` block both before the type and inside it. This is redundant and will drift out of sync.

### 19. `FileLoadOptions` uses `HashSet<string>` with a manual dot-prefix convention
```csharp
public HashSet<string> AllowedExtensions { get; init; } = new(StringComparer.OrdinalIgnoreCase);
```
The validator enforces that each entry starts with `'.'` and is > 1 char, but the type itself gives no such guarantee. A custom struct like `FileExtension` (wrapping a `string`, validating the dot in its constructor) would make invalid data unrepresentable at the type level rather than relying on a runtime validator.

### 20. `OllamaChatClientBuilder` is a concrete sealed class implementing an interface
```csharp
public sealed class OllamaChatClientBuilder() : IOllamaChatClientBuilder
```
If the class is `sealed` and is the *only* implementation, the interface adds indirection without polymorphic benefit. Either make it a static helper (like the other extension classes) or drop the `sealed` modifier if you intend to allow substitution.
