# Missing / Suggested Custom Middleware

Your pipeline currently has **one** concrete middleware (`StageTimingMiddleware`). The architecture clearly anticipates more — the strongest evidence is this line in `StageTimingMiddleware`:

```csharp
RetryCount = 0, // populate via a separate retry middleware if needed
```

That comment is a TODO in disguise. Below are the middleware I'd implement, ordered by priority.

---

## 1. `RetryMiddleware` (highest priority)

**Why:** Right now the Polly `IAsyncPolicy` is applied *inside* the `core` Func in `ExecuteAsync`, which means it sits **below** the middleware onion. That means `StageTimingMiddleware` measures the *total* time including all retries, and `StageMetric.RetryCount` is hardcoded to `0`. A dedicated middleware lets you:

- count actual retries,
- log each attempt,
- keep timing per-attempt vs. total,
- swap policies per stage without touching the runner.

```csharp
/// <summary>
/// Wraps stage execution in a Polly retry policy and records the final
/// attempt count into <see cref="StageMetric.RetryCount"/>.
/// </summary>
public sealed class RetryMiddleware(Serilog.ILogger logger)
{
    public async Task Invoke<TContext>(
        StageExecutionContext<TContext> context,
        Func<Task> next,
        CancellationToken cancellationToken)
        where TContext : class
    {
        cancellationToken.ThrowIfCancellationRequested();
        ArgumentNullException.ThrowIfNull(context);
        ArgumentNullException.ThrowIfNull(next);

        var policy = context.Stage.RetryPolicy;          // IPipelineStage already exposes it
        if (policy is null)
        {
            await next().ConfigureAwait(false);
            return;
        }

        var attempt = 0;
        await policy.ExecuteAsync(async ct =>
        {
            attempt++;
            logger.Debug("Stage {Name} – retry attempt {Attempt}", context.Stage.Name, attempt);
            await next().ConfigureAwait(false);
        }, cancellationToken).ConfigureAwait(false);

        // Overlay the real retry count onto whatever the timing middleware wrote.
        if (context.Metric is not null)
            context.Metric = context.Metric with { RetryCount = attempt };
        else
            context.Metric = new StageMetric
            {
                StageName  = context.Stage.Name,
                RetryCount = attempt
            };
    }
}
```

Registration becomes:

```csharp
runner
    .UseMiddleware(new StageTimingMiddleware(logger).Invoke)   // outer: timing
    .UseMiddleware(new RetryMiddleware(logger).Invoke);         // inner:  retry
```

Because the onion runs **last-registered first**, `RetryMiddleware` wraps the actual stage call and `StageTimingMiddleware` wraps the retry loop — exactly the layering you want.

> **Note:** You'll need `StageEntry<TContext>` to either stop carrying `IAsyncPolicy` or to expose the stage's own `RetryPolicy` property so the middleware can read it. Currently `IPipelineStage<TContext>` already has `RetryPolicy => null` (see `BrandingStage`), so the stage is the natural owner.

## 2. `ExceptionHandlingMiddleware`

**Why:** `ExecuteAsync` currently has an inline `catch` that wraps everything in a `PipelineStageException`. As a middleware you can:

- normalise exception types *before* they bubble,
- add structured logging (Serilog self-describing events),
- populate `StageMetric.Error` even when the timing middleware hasn't run yet (defence in depth),
- attach diagnostic context (stage name, index, correlation ID).

```csharp
public sealed class ExceptionHandlingMiddleware(Serilog.ILogger logger)
{
    public async Task Invoke<TContext>(
        StageExecutionContext<TContext> context,
        Func<Task> next,
        CancellationToken cancellationToken)
        where TContext : class
    {
        try
        {
            await next().ConfigureAwait(false);
        }
        catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
        {
            throw; // let cancellation propagate cleanly
        }
        catch (Exception ex)
        {
            logger.Error(ex,
                "Stage [[{Index}/{Total}]] {Name} failed: {Message}",
                context.StageIndex + 1,
                context.StageTotal,
                context.Stage.Name,
                ex.Message);

            // Overlay error into metric if timing middleware already set one,
            // otherwise create a minimal record.
            context.Metric = context.Metric is { } m
                ? m with { Success = false, Error = ex.Message }
                : new StageMetric { StageName = context.Stage.Name, Success = false, Error = ex.Message };

            throw new PipelineStageException(context.Stage.Name, ex);
        }
    }
}
```

With this in place you can **delete** the `try/catch` block from `ExecuteAsync` — the runner becomes purely orchestration.

## 3. `MetricsSummaryMiddleware` (pipeline-level, not per-stage)

**Why:** `StageMetric` is per-stage. Nothing currently aggregates them into a run-level report. A final "sink" middleware that reads all populated metrics after the last stage gives you a one-line console summary or a structured log event.

```csharp
public sealed class MetricsSummaryMiddleware(Serilog.ILogger logger)
{
    public async Task Invoke<TContext>(
        StageExecutionContext<TContext> context,
        Func<Task> next,
        CancellationToken cancellationToken)
        where TContext : class
    {
        await next().ConfigureAwait(false);

        // Only the LAST stage's invocation triggers the summary.
        if (context.StageIndex + 1 != context.StageTotal) return;

        // Pull metrics from the context (you'd need a collection on TContext
        // or a shared accumulator — see note below).
        logger.Information(
            "Pipeline summary – {Stages} stage(s), {Failed} failed, total {Total}",
            context.StageTotal,
            // count from a ConcurrentDictionary<Guid, StageMetric> on the context
            TimeSpan.Zero); // placeholder – sum from context
    }
}
```

> **Design note:** `StageExecutionContext<TContext>` currently carries a single `StageMetric?`. For a summary you'd either (a) add `IList<StageMetric> AllMetrics` to your *domain* context (`QuestionPipelineContext` / `EmbeddingContext`) and have the timing middleware append, or (b) introduce a `MetricsSink` that the runner writes to after the loop.

## 4. `ProgressMiddleware` (nice-to-have)

Useful for long-running pipelines (embedding thousands of files). Writes a `█▓▒░`-style bar or a simple `[[3/7]] Embedding… 12s` line.

```csharp
public sealed class ProgressMiddleware
{
    public async Task Invoke<TContext>(
        StageExecutionContext<TContext> context,
        Func<Task> next,
        CancellationToken cancellationToken)
        where TContext : class
    {
        var label = $"[[{context.StageIndex + 1}/{context.StageTotal}]] {context.Stage.Name}";
        Console.Write($"{label} … ");
        var sw = Stopwatch.StartNew();
        await next().ConfigureAwait(false);
        Console.WriteLine($"✓ {sw.Elapsed:hh\\:mm\\:ss}");
    }
}
```

## 5. `ValidationMiddleware` (defence-in-depth)

Pre-condition / post-condition checks on the context. Example: ensure `QuestionPipelineContext.Questions` is non-null before the *answer* stage runs.

```csharp
public sealed class ValidationMiddleware<TContext>(
    Func<TContext, bool> preCondition,
    string failureMessage)
{
    public Task Invoke<TCtx>(
        StageExecutionContext<TCtx> context,
        Func<Task> next,
        CancellationToken cancellationToken)
        where TCtx : class
    {
        if (context.Context is TContext typed && !preCondition(typed))
            throw new PipelineStageException(context.Stage.Name,
                new InvalidOperationException(failureMessage));
        return next();
    }
}
```

## Recommended full stack

```csharp
runner
    .UseMiddleware(new ExceptionHandlingMiddleware(logger).Invoke)  // outermost – catches everything
    .UseMiddleware(new StageTimingMiddleware(logger).Invoke)        // timing (includes retries)
    .UseMiddleware(new RetryMiddleware(logger).Invoke)              // retry (inner)
    .UseMiddleware(new ProgressMiddleware().Invoke);                // innermost – wraps the raw stage
```

Onion execution order (innermost first):
```
ExceptionHandling → StageTiming → Retry → Progress → [[stage.ExecuteAsync]]
```
