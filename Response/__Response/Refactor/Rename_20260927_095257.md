# Ragnar – Naming Recommendations

Below are concrete, prioritised renames grouped by impact. I focus on names that actively mislead a reader about *what* is happening, *what* a type represents, or *how* it fits the broader .NET conventions.

---

## 1. Highest-impact: names that actively mislead

| Current name | Suggested rename | Why |
|---|---|---|
| `CodeDocument.Dictionary` (property) | `CodeDocument.AsPayload()` / `.AsMetadata()` | A property literally called **Dictionary** on a domain object tells the reader nothing. It builds the Qdrant point payload. |
| `Question.IsActive(string, string, QuestionCategory)` | `Question.CreateActive(...)` | Reads like a *query* ("is it active?") but is a *factory method*. `CreateActive` / `CreateDisabled` make intent unambiguous. |
| `Question.IsDisabled(...)` | `Question.CreateDisabled(...)` | Same problem; also inconsistent with the `IsActive` sibling. |
| `Question.IsEnabled` (record field) | `Question.IsActive` / `Question.ShouldProcess` | "Is a question *enabled*?" is not natural English. "Should this be processed?" is the real meaning. |
| `IWriter` (file-writing interface) | `IFileWriter` | `IWriter` collides with Spectre's `IOutputWriter` and with `ResponseWriter`. A reader sees `IWriter` and cannot tell if it's console, file, or network. |
| `FileParser` (concrete class in *Ragnar.Embedding*) | `MarkdownChunkParser` / `TextFileParser` | There is also `BaseFileParser`, `CSharpFileParser`, `IFileParser`, **and** `IFileParseFactory`. A bare `FileParser` that actually splits Markdown into chunks is the most confusing entry. |
| `questionEmbedding` (param in `QuestionExecutionStage`) | `contextRetriever` / `vectorSearch` | The variable name says "embedding" but the object does *retrieval*. It never embeds a question here. |
| `OllamaClientFactory.CreateHttpClient` | `OllamaClientFactory.CreateOllamaHttpClient` / `.ConfigureHttpClient` | "CreateHttpClient" suggests a bare `new HttpClient()`. It actually sets `BaseAddress`, `Timeout`, etc. |
| `IRecordParser<T>` (generic interface) | `ICsvQuestionParser` / `IQuestionFileParser` | The generic makes it look like a universal CSV→POCO mapper. In practice it only parses `QuestionRecord` from CSV. |
| `QuestionRecord` | `CsvQuestionRow` / `QuestionCsvRow` | Signals it's a *row mapping*, not a domain entity (the domain entity is `Question`). |

## 4. Structural / naming-pattern observations

1. **"Writer" collision.** You have `IWriter` (file I/O), `IOutputWriter` (console), `ResponseWriter` (orchestrates both), and `FileWriter` (implements `IWriter`). A reader cannot tell which "writer" is which.  
   **Fix:** Rename the file-I/O interface to `IFileWriter`, keep `IOutputWriter` for console, and rename `ResponseWriter` → `ResponseSaver` or `ResponsePersister` to break the "writer" chain.

2. **`required` keyword on `RagnarConfig`.** Using `required` is good, but the class is bound via `IOptions<RagnarConfig>`. The conventional .NET name for such a class is `RagnarOptions` (matching `Microsoft.AspNetCore.Mvc.MvcOptions`, etc.). Rename to `RagnarOptions` and the binding becomes `IOptions<RagnarOptions>`.

3. **`IRecordParser<T>` generic.** It only ever resolves to `IRecordParser<QuestionRecord>`. If you might add other CSV sources, keep the generic but rename to `ICsvRecordParser<T>`. If not, specialise it: `ICsvQuestionParser`.

4. **`extension()` blocks (C# 14 preview).** Several files use the new `extension(Type)` syntax inside a static class (e.g. `CodeDocumentExtensions`, `QuestionExtensions`, `AssemblyExtensions`, `StringExtensions`). This is fine, but the containing static class name + the extension target should form a clear compound: `CodeDocumentExtensions` ✔, `AssemblyExtensions` ✔, but `StringExtensions` wrapping *only* XML-comment character counting is a misnomer → `XmlCommentExtensions` or fold into `CodeDocumentExtensions`.

5. **Inconsistent "Is" prefixes on factory methods.** `Question.IsActive` / `Question.IsDisabled` look like queries. Switching to `CreateActive` / `CreateDisabled` (or `NewEnabled` / `NewDisabled`) removes the ambiguity and matches the `Guard.Against` + factory pattern used elsewhere.

6. **`Styles.Blue`, `Styles.BoldSteelBlue`, `Styles.Cyan`.** These are Spectre.Console styles, so the names are fixed. No change needed, but a `RagnarStyles` static class with named constants (`Title`, `Tagline`, `Version`, `Progress`) would make call-sites in `ApplicationHeader` and `QuestionExecutionStage` self-documenting.
