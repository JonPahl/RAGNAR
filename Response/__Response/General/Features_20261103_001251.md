## Recommended Feature: Incremental Indexing with File-Change Detection

After reviewing the full pipeline — `FileDiscoveryService` → `CodeParserFactory` → embedding generation → `VectorStoreWriter` into Qdrant — the most impactful feature to add would be **incremental indexing via content-hash tracking**. Right now, every run appears to re-parse, re-embed, and re-upsert *every* eligible file. For a codebase of even a few thousand C# files, that means hundreds of Ollama embedding round-trips that produce identical vectors for files that haven't changed.

### Why it matters

| Current behaviour | With incremental indexing |
|---|---|
| Full re-embed on every invocation | Only changed/new files are embedded |
| `VectorStoreWriter` upserts all points (Qdrant accepts it, but it's wasted I/O + CPU on the server) | Upsert *new/changed* points; **delete** points whose source file was removed |
| Wall-clock time scales with total file count | Scales with the *delta* (usually < 5 % of files) |

### Sketch of the design

1. **`IndexManifest` (new small record / SQLite or JSON side-car)**

   ```csharp
   public sealed record IndexManifestEntry(
       string FilePath,      // normalised relative path
       ulong  ContentHash,   // SHA-256 of file bytes
       Guid   QdrantPointId, // the point ID we wrote
       DateTime IndexedAtUtc);

   public sealed class IndexManifest
   {
       public Dictionary<string, IndexManifestEntry> Entries { get; } = new(StringComparer.OrdinalIgnoreCase);
       // load / save / diff helpers
   }
   ```

2. **New pipeline stage: `IndexDiffStage`** (inserted after `FileDiscoveryStage`, before parsing)

   ```csharp
   public sealed class IndexDiffStage(ILogger logger, IManifestStore manifest)
       : IPipelineStage<EmbeddingContext>
   {
       public string Name => "Index Diff";

       public Task ExecuteAsync(EmbeddingContext ctx, CancellationToken ct)
       {
           var allFiles   = ctx.DiscoveredFiles;           // from discovery stage
           var manifest   = manifest.Load();

           var toEmbed    = allFiles
               .Where(f => !manifest.Entries.TryGetValue(f, out var e)
                          || e.ContentHash != ComputeHash(f))
               .ToList();

           var toDelete   = manifest.Entries.Keys
               .Where(f => !allFiles.Contains(f))          // file removed from disk
               .ToList();

           ctx.FilesToEmbed  = toEmbed;
           ctx.PointsToDelete = toDelete
               .Select(f => manifest.Entries[[f]].QdrantPointId)
               .ToList();

           logger.Information("Index diff: {Embed} to embed, {Delete} to remove, {Skip} unchanged",
               toEmbed.Count, toDelete.Count, allFiles.Count - toEmbed.Count);
           return Task.CompletedTask;
       }
   }
   ```

3. **Wire it into `PipelineRunner`**

   ```csharp
   runner
       .AddStage(new BrandingStage(logger, header))
       .AddStage(new FileDiscoveryStage(logger, discovery, config))
       .AddStage(new IndexDiffStage(logger, manifestStore))   // ← new
       .AddStage(new ParseStage(logger, parserFactory, config))
       .AddStage(new EmbedStage(logger, embedding, config))
       .AddStage(new StoreStage(logger, vectorWriter, config))
       .UseTiming(new StageTimingMiddleware(logger));
   ```

4. **`StoreStage` gains a delete pass**

   ```csharp
   // after upserting new points:
   if (ctx.PointsToDelete.Count > 0)
       await vectorWriter.DeletePointsAsync(ctx.PointsToDelete, ct);
   ```

5. **Persist the manifest** after a successful store:

   ```csharp
   manifest.Save(ctx.FilesToEmbed.Select(f => new IndexManifestEntry(
       f, ComputeHash(f), /* point id from upsert response */, DateTime.UtcNow)));
   ```

### What you get for free

* **Faster cold-starts** for unchanged code — only the diff is touched.
* **Correct deletion** — files you delete from the repo no longer haunt Qdrant as stale vectors.
* **Composable with the existing middleware chain** — `StageTimingMiddleware` already wraps every stage, so the diff stage's duration shows up in logs automatically.
* **Trivially testable** — `IndexDiffStage` is a pure function of `(fileList, manifest)` → `(toEmbed, toDelete)`; no I/O mocking needed beyond the hash computation.
* **Extensible** — later you can extend the manifest to store per-segment hashes (a single file might produce multiple `CodeDocument` chunks from the Roslyn parser), enabling *segment-level* re-embedding instead of file-level.

### Optional follow-on enhancements (same area)

| Enhancement | Effort | Benefit |
|---|---|---|
| Segment-level hashing (hash each `CodeDocument` text, not the whole file) | Medium | Re-embed only the changed method/class, not the entire file |
| `--force-reindex` CLI flag that bypasses the diff stage | Trivial | One-liner escape hatch for model upgrades |
| Store the embedding model name in the manifest | Trivial | Auto-invalidate all points when the model changes (e.g. `nomic-embed-text` → `mxbai-embed-large`) |
| Progress bar showing "123/456 files embedded" during the diff pass | Trivial | Better UX for the (now much smaller) embed loop |

This feature slots cleanly into the existing stage/middleware architecture, requires no new external dependencies (SHA-256 is in `System.Security.Cryptography`), and turns what is currently an O(N) operation into an O(Δ) one — which, for real-world C# solutions, is the single biggest usability win.
