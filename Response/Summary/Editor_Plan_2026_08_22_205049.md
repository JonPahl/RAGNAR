### Summary: C# `.editorconfig` Implementation Plan

**Core Objective:** Establish consistent code formatting, syntax preferences, and naming conventions across all projects in the repository using Microsoft’s native `.editorconfig` standard. This approach eliminates drift between Visual Studio, Rider, and VSCode without requiring external linting tools.

#### Key Insights
*   **Native Enforcement:** Leverage Roslyn analyzers for naming rules (enforced at compile-time) and `.editorconfig` for formatting (enforced at save/time).
*   **Modern C# Focus:** Prioritize idiomatic modern syntax (C# 10–14), including file-scoped namespaces, external `using` directives, `var` inference, null propagation, and throw expressions.
*   **Gradual Rollout Strategy:** Begin with `suggestion` severity to allow team adaptation before escalating to warnings or errors in CI/CD.

#### Core Conventions Enforced
1.  **Formatting:** 4-space indentation, braces on new lines, tight operator spacing.
2.  **File Standards:** UTF-8 with BOM (standard for Windows/.NET), LF line endings, no trailing whitespace, final newline required.
3.  **Naming:**
    *   Public APIs: `PascalCase`
    *   Private Fields: `_camelCase`
    *   Locals/Parameters: `camelCase`
    *   Interfaces: `IPascalCase`
4.  **Modern Syntax:** File-scoped namespaces, external usings, implicit nullable references (if applicable).

*   **IDE Setup:** Enable “Format on Save” in VS/Rider/VSCode. Ensure Roslyn analyzers are active (default in modern SDKs).
*   **Severity Progression:** Start with `suggestion`. Promote to `warning` only after team alignment and automated formatting are stable.
*   **Documentation:** Add the `.editorconfig` configuration to `CONTRIBUTING.md` for onboarding clarity.
*   **Monitoring:** Track IDE warning counts to gauge adoption rate before escalating severity levels.

This plan ensures immediate consistency, leverages native .NET tooling, and provides a low-friction path to full enforcement across development and CI workflows.
