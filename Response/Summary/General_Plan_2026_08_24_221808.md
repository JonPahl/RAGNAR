### Executive Summary
The recommended strategy focuses on transitioning the codebase from exception-driven control flow to a modern, resilient architecture using **Minimal Hosting**, **Feature-based layering**, and the **Result Pattern**. The goal is to create a cohesive, testable system that supports hot-reloading configuration and robust external service integration (Ollama/Qdrant).

### 1. Architectural Patterns & Layering
A clear mapping of patterns to specific layers is recommended to enforce separation of concerns:
*   **Bootstrap:** Use Minimal Hosting with a Facade pattern to simplify the dependency injection (DI) wiring.
*   **Configuration:** Adopt **Record Types** combined with `IOptionsMonitor` for type-safe settings and hot-reload capabilities.
*   **Data Ingestion:** Implement a **Pipeline Pattern** wrapped in the **Result Pattern**. This ensures file/CSV loading is composable, resilient to errors (like missing paths), and streamable (`IAsyncEnumerable`).
*   **AI/Vector Services:** Use the **Builder Pattern** alongside the Chain of Responsibility for fluent setup of Ollama and Qdrant clients.
*   **Output:** enforce **Atomic Writes** (temp file -> move) to prevent data corruption during response persistence.

### 2. Consolidated Implementation Roadmap
The execution plan is divided into four prioritized phases:

*   **Phase 1: Foundation & Structure (Priority High)**
    *   Restructure the project into feature-based layers (`Core`, `Infrastructure`, `Application`, etc.).
    *   Refactor `Program.cs` to use Minimal Hosting.
    *   Pin preview package versions (xUnit v3, CsvHelper 33+, Serilog 4+).
*   **Phase 2: Resilience & Data Flow**
    *   Replace standard exceptions with `Result<T>` for expected control flow (e.g., empty directories).
    *   Convert synchronous I/O to asynchronous streams (`IAsyncEnumerable`/`System.IO.Pipelines`).
    *   Implement batching and atomic writes.
    *   Integrate **Polly** (Resilience) for retry/circuit-breaking logic around external calls.
*   **Phase 3: Configuration & Builders**
    *   Standardize builders (`Config`, `AI`, `Vector`) and register them via a unified DI extension method.
    *   Externalize prompts/templates to JSON/YAML with runtime reloading.
*   **Phase 4: Testing & Observability (Ongoing)**
    *   Upgrade to xUnit v3 with FluentAssertions.
    *   Use `Testcontainers` for integration tests against Ollama and Qdrant.
    *   Enforce strict `.editorconfig` rules (e.g., required keywords, primary constructors).

### 3. Key Architectural Decisions & Trade-offs
*   **Exceptions vs. Result Pattern:** Reserve exceptions for true errors (network failure, auth), but strictly use `Result<T>` for expected operational control flow to maintain composable async code.
*   **Builder Strategy:** Keep domain-specific builders (Config vs. AI) to avoid bloat, but unify their registration via a single fluent extension (`services.AddRagnarPipelines(cfg)`).
*   **Pipeline Composition:** Stick to explicit step lists for now; avoid over-engineering with MediatR unless the stage count exceeds three.
*   **DI Lifetimes:** Use `Singleton` for clients (backed by `IHttpClientFactory`) and `Scoped` for pipelines/writers to prevent socket exhaustion and manage state correctly.
