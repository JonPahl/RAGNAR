### 1. `SummarizeSaveResponse` — Mutable Singleton State Corrupts Output Paths

**Impact: High | Effort: Low**

```csharp
private string? _responseDir;

public async Task<string> WriteResponseAsync(ResponseRecord details, CancellationToken cancellationToken)
{
    var sourceDir = Path.GetDirectoryName(details?.Question?.Filename) ?? Directory.GetCurrentDirectory();
    _responseDir ??= Directory.CreateDirectory(Path.Join(sourceDir, "Response")).FullName;
    // ...
    var summaryPath = Path.Join(_responseDir, fileName);
```

**The problem:** `_responseDir` is cached via `??=` on the *first* call and then locked in for every subsequent call for the lifetime of the object. Because this class is registered as a singleton (it implements `IResponseWriter` resolved from DI), the directory of the *first* question processed determines where **all** later responses are written. If questions originate from different source trees (e.g., `src/Api/Controller.cs` and `src/Worker/Handler.cs`), every response after the first lands in `src/Api/Response/`. Worse, two different questions from different files that share the same file-name stem will **silently overwrite each other**. The `??=` assignment is also not atomic under concurrent execution.

**Remediation (~30 min):** Remove the field entirely. Compute the path on every call:

```csharp
public async Task<string> WriteResponseAsync(ResponseRecord details, CancellationToken cancellationToken)
{
    var sourceDir = Path.GetDirectoryName(details?.Question?.Filename) ?? Directory.GetCurrentDirectory();
    var responseDir = Directory.CreateDirectory(Path.Join(sourceDir, AppDefaults.ResponseDirectoryName)).FullName;
    var fileName = $"{Path.GetFileNameWithoutExtension(details?.Question?.Filename)}_summary.md";
    var summaryPath = Path.Join(responseDir, fileName);
    var content = string.Format(_template, details?.Answer, DateTime.UtcNow.ToString("O"));
    await File.WriteAllTextAsync(summaryPath, content, cancellationToken).ConfigureAwait(false);
    return summaryPath;
}
```

No state, no race, correct per-file placement.

### 2. `EmbeddingGeneratorService` — Unreachable Timeout Handler Masks Real Failures

**Impact: High | Effort: Low**

```csharp
var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
timeoutCts.CancelAfter(configuration.Value.OllamaOptions.Timeout);
try
{
    var result = await generator.GenerateAsync(input, cancellationToken: timeoutCts.Token).ConfigureAwait(false);
    return result.Vector.ToArray();
}
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    throw;                                   // only fires if the *caller* cancelled
}
catch (TimeoutException ex)                  // ← NEVER reached
{
    logger.Fatal(ex, "Embedding generation timed out.");
    throw;
}
```

**The problem:** `CancellationTokenSource.CancelAfter` does **not** throw `TimeoutException`. It throws `OperationCanceledException` (or `TaskCanceledException` for `Task`-based APIs). Because the first catch filter is `when (ct.IsCancellationRequested)`, and the caller's token has *not* been cancelled (only the timeout CTS fired), that catch is skipped. The second catch targets `TimeoutException`, which will never be the type thrown. The exception therefore propagates as a bare `OperationCanceledException` with no logging, no context, and no distinction from a genuine user-initiated cancel. In production this produces silent, unlogged failures that are indistinguishable from the user pressing Ctrl+C.

**Remediation (~15 min):**

```csharp
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    throw; // genuine caller cancellation – rethrow as-is
}
catch (OperationCanceledException ex)
{
    // timeoutCts fired, but the caller did not cancel → this is a timeout
    logger.Fatal(ex, "Embedding generation timed out after {Timeout}", configuration.Value.OllamaOptions.Timeout);
    throw new TimeoutException("Embedding generation timed out.", ex);
}
```

### 3. `QuestionCombineBuilder` + `IQuestionBuilder` — Shared Mutable Builder with No Isolation

**Impact: High | Effort: Moderate**

```csharp
// In GetCsvFilesAsync – the builder's return value is discarded:
questionBuilder.WithText(csv.Text).WithFileName(csv.Filename).SetCategory(csv.Category).SetActive(csv.IsEnabled);
Questions.Add(questionBuilder.Build());   // ← reads from shared state
```

**The problem:** `IQuestionBuilder` is injected as a single instance. The `With…` chain mutates that instance's internal state (text, filename, category, active flag). Three distinct hazards follow:

| Hazard | Consequence |
|---|---|
| **Interleaved writes** (two pipeline branches calling `GetCsvFilesAsync` / `GetFileConfig` concurrently) | Thread A sets `Text="A"`, Thread B overwrites with `Text="B"`, Thread A calls `Build()` → gets `{Text:"B", FileName:"a.cs"}` — a Frankenstein question. |
| **Accumulation** | `Build()` does not reset the builder. Calling `GetCategories()` → `GetFileConfig()` → `Build()` appends to the ever-growing `Questions` list; a second call to `Build()` returns *duplicated* entries. |
| **`Clear()` is misleading** | `Clear()` empties the list and then returns `Questions.Count != 0`, which is **always `false`**. Any caller branching on this result gets the wrong answer. |

**Remediation (~1–2 h):**

1. Make `IQuestionBuilder` a **scoped, single-use** object: register it as `AddScoped` (not singleton) and call `Build()` exactly once per instance.
2. In `QuestionCombineBuilder`, create a **fresh** builder per question instead of reusing the injected one:

```csharp
public IQuestionSourceBuilder GetFileConfig()
{
    var fcl = new FileConfigLoader();
    foreach (var config in fcl.LoadQuestions())
    {
        var item = questionBuilder
            .WithText(config.Text)
            .WithFileName(config.Filename)
            .SetCategory(config.Category)
            .SetActive(config.IsEnabled)
            .Build();               // consume immediately
        Questions.Add(item);
    }
    return this;
}
```

3. Add a `[[ThreadStatic]]` guard or wrap the mutation + `Build()` in a `lock` if the builder must remain shared.
4. Fix `Clear()`:

```csharp
public bool Clear()
{
    var hadItems = Questions.Count > 0;
    Questions.Clear();
    return hadItems;   // return the *pre-clear* state
}
```
