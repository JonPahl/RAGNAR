# Top 3 Most Critical Technical Debt Items

## 1. `ConsoleTableBuilder` — Latent `NotImplementedException` Crash

**Impact: Critical | Effort: Low (~15 min)**

```csharp
// ConsoleTableBuilder.cs
List<string> ITableBuilder.Columns => throw new NotImplementedException();
List<List<string>> ITableBuilder.Rows => throw new NotImplementedException();
```

The class already exposes `Columns` (as `List<string>`) and `Rows` (as `List<string[[]]>`) as public properties, yet the *explicit* interface implementations for `ITableBuilder.Columns` and `ITableBuilder.Rows` both throw `NotImplementedException`. Any consumer that holds a reference typed as `ITableBuilder` and accesses `.Columns` or `.Rows` will crash at runtime.

Worse, there's a **type mismatch**: the backing store is `List<string[[]]>` but the interface contract demands `List<List<string>>`. This isn't a one-liner; it requires either:

- Changing the backing collection to `List<List<string>>`, or
- Implementing the explicit interface members with a projection (`Rows.Select(r => [[..r]]).ToList()`).

**Why it's #1:** It's a guaranteed `UnhandledException` in production for any code path that uses the polymorphic interface. The fact that `ConsoleTableRenderer` calls `Table.ToTable()` internally (which uses the concrete `Columns`/`Rows`) masks the bug in the happy path, but the moment another consumer (a test helper, a different renderer, a future report exporter) resolves through `ITableBuilder`, the app dies.

**Remediation sketch:**

```csharp
List<string> ITableBuilder.Columns => [[..Columns]];
List<List<string>> ITableBuilder.Rows => Rows.Select(r => [[..r]]).ToList();
```

## 2. `PathResolver` vs. `ResponseWriter` — Contradictory Directory-Existence Contract

**Impact: High (fresh-install crash) | Effort: Low (~10 min)**

```csharp
// PathResolver.cs
public string ResolveResponseDirectory(QuestionCategory? category)
{
    var responseDir = Path.Join(_applicationOptions.SourceDirectory, _applicationOptions.OutputFolder);
    if (!Directory.Exists(responseDir))
        throw new DirectoryNotFoundException(responseDir);   // ← throws before writer can create it
    return Path.Join(responseDir, baseDir);
}
```

```csharp
// ResponseWriter.cs
public async Task<string> WriteResponseAsync(SaveDetails details, CancellationToken ct)
{
    var directory = pathResolver.ResolveResponseDirectory(details.Question.Category); // ← explodes here
    Directory.CreateDirectory(directory);   // ← never reached on first run
    // …
}
```

On a clean machine (no prior `Response/` folder under `SourceDirectory`), the **first** call to write any response throws `DirectoryNotFoundException` before `Directory.CreateDirectory` can execute. The two classes have a contradictory contract: the resolver *requires* the directory to exist; the writer *assumes* it can create it.

**Why it's #2:** It's a guaranteed failure for every first-run scenario (CI/CD, new developer clone, production deployment). The unit tests in `ResponseWriterTests` pass only because they mock `IPathResolver`, which hides the real contract mismatch.

**Remediation:** Remove the `throw` from `PathResolver` (it should be a pure path-computation method) and let `ResponseWriter` own the `CreateDirectory` responsibility. Alternatively, move the creation logic *before* the resolver call and have the resolver simply compute the string.

## 3. `QuestionExecutionStage.LoadQuestionsAsync` — God-Method Violating SRP and Blocking Async I/O

**Impact: Medium-High (untestable, unextensible, blocks thread pool) | Effort: Medium (~1–2 hrs refactor)**

```csharp
// QuestionExecutionStage.cs (the "Ask Questions" stage)
private async Task<IReadOnlyList<Core.Model.Question>> LoadQuestionsAsync(CancellationToken ct)
{
    //TODO Make loading questions be its own stage.
    builder.GetCategories().GetFileConfig();
    var pluginDir = Path.Join(AppContext.BaseDirectory, "Plugins");
    await builder.GetCsvFilesAsync(pluginDir, ct).ConfigureAwait(false);
    builder.WithCategoryFilter();
    var sorted = builder.Build();
    ShowTable(sorted);          // ← synchronous console rendering inside async method
    return [[..sorted]];
}
```

This single private method is responsible for **five** distinct concerns:

| Concern | Where it belongs |
|---|---|
| Resolving plugin directory path | Configuration / `IPathResolver` |
| Discovering CSV files | A dedicated `QuestionDiscoveryStage` |
| Applying category filters | `IQuestionSourceBuilder` (already there) |
| Rendering a live Spectre table | `IOutputWriter` / a reporting service |
| Returning the loaded list | The stage itself |

The `ShowTable` call uses `AnsiConsole.Live(table).Start(…)` which is a **synchronous blocking** rendering loop inside an `async` method. On a high-volume run (thousands of questions) this holds a thread-pool thread hostage and prevents the `CancellationToken` from being observed between rows.

The existing unit tests (`AskQuestionsStageTests`) have to mock **every** builder method in sequence (`GetCategories → GetFileConfig → GetCsvFilesAsync → WithCategoryFilter → Build`), which is brittle and confirms the coupling. The `//TODO` comment acknowledges the problem, but it's been sitting unaddressed.

**Why it's #3:** It doesn't crash the app today, but it makes the stage impossible to (a) unit-test the loading logic in isolation, (b) swap the CSV source for a different `IQuestionProvider` without touching rendering code, and (c) add progress/cancellation to the table render. As the question set grows, the blocking render becomes a user-visible hang.

**Remediation outline:**

1. Extract a `QuestionLoadingStage : IPipelineStage<QuestionContext>` that owns discovery, filtering, and returns the list on the context.
2. Move `ShowTable` into an `IOutputWriter` extension or a dedicated `IReportRenderer` and make it async (`foreach` with `await Task.Yield()` or a `Channel`-based producer/consumer).
3. Slim `QuestionExecutionStage` down to: read questions from context → for each, retrieve context → call RAG orchestrator → write response.
