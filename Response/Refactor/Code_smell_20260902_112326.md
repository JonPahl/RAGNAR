## 2. Inconsistent Test Assertion Style

**Where:** `SystemPromptProviderTests`, `ExtensionMethodsTests`, `StylesTests`, `FileValidatorTests`, `BaseFileParserTests`

```csharp
// Flushing between two incompatible assertion libraries
provider.System.Should().NotBeNull();          // FluentAssertions
Assert.NotEmpty(provider.System);               // xUnit
provider.System.Should().Contain(".NET 10");   // FluentAssertions

// And in another test:
result.Should().Contain("***");                // FluentAssertions
Assert.Equal(expected, result);                // xUnit
```

**Fix:** Pick **one** assertion library per project (most teams standardise on xUnit `Assert` or FluentAssertions `Should()`). Remove the other. A quick rule:

| Library | When to use |
|---|---|
| `Assert.*` | Simple equality, null checks |
| `Should()` | Complex chains, soft assertions, collection matching |

Do not mix them in the same test method.

## 5. Inconsistent Async Return Types (`Task` vs `ValueTask`)

**Where:** `BaseFileParser.ReadFileAsync` returns `ValueTask<string>`, while `OllamaChatResponse.GenerateResponse` returns `Task<string>`, `VectorStoreRepository.UpsertBatchAsync` returns `Task<UpdateResult>`, etc.

**Fix:** Establish a project-wide guideline:

- **Public API surface** (interfaces, library entry points) → `Task<T>`
- **Internal hot-path helpers** where an allocation-free return is meaningful → `ValueTask<T>`
- Never mix both in the same interface.

In practice, `ValueTask` is rarely worth the complexity outside of very high-throughput scenarios. Consider standardising on `Task<T>` everywhere unless a benchmark proves otherwise.

## 6. Inconsistent Error-Handling Strategies

**Where:** `VectorStoreRepository.UpsertBatchAsync`, `SummaryService.SaveResponseAsync`, `BaseFileParser.ReadFileAsync`

```csharp
// VectorStoreRepository – logs Fatal, returns a sentinel result
catch (Exception ex) when (ex is not OperationCanceledException)
{
    logger.Fatal(ex, "Failed to upsert embeddings to Qdrant.");
    return new UpdateResult { Status = UpdateStatus.UnknownUpdateStatus };
}

// SummaryService – logs Error, silently swallows
catch (Exception ex)
{
    _logger.Error(ex, ex.Message);
}
// caller has no idea the write failed

// BaseFileParser – rethrows as a different exception type
catch (Exception ex)
{
    logger.Error(ex, "Failed to read file: {FilePath}", filePath);
    throw new InvalidOperationException($"Could not read file '{filePath}'.", ex);
}
```

Three different strategies in three adjacent services. A caller of `SummaryService` will believe the summary was saved when it wasn't.

**Fix:** Choose **one** policy per layer:

| Layer | Policy |
|---|---|
| Repository / I/O | Catch domain-specific exceptions, log at `Error`, **rethrow** (or wrap in a typed `DomainException`) so the caller can decide. |
| Service | Catch, log at `Warning`, return a result object *only if* the operation is inherently best-effort. |
| UI / Pipeline stage | Catch at the top level, log `Fatal`, surface to the user. |

For `SummaryService.SaveResponseAsync`, at minimum return a `bool` or throw so the caller (`SummarizeAllResponsesAsync`) can report failure.

## 12. Duplicated Question-Loading Logic

**Where:** `QuestionCombineBuilder` has three near-identical methods (`GetCategories`, `GetFileConfig`, `GetCsvFileAsync`) that all follow the same pattern: *load records → map to `Question` → append to `Questions` list*.

**Fix:** Introduce a common `IQuestionSource` / `IQuestionProvider` interface (you already have `IQuestionProvider` for CSV!) and register all sources:

```csharp
public interface IQuestionProvider
{
    Task<IEnumerable<Question>> LoadQuestionsAsync(CancellationToken ct);
}

// QuestionCombineBuilder becomes:
public async Task<IReadOnlyList<Question>> BuildAsync(CancellationToken ct)
{
    var all = await Task.WhenAll(_providers.Select(p => p.LoadQuestionsAsync(ct)));
    return all.SelectMany(x => x).Where(q => q.IsEnabled)
              .OrderBy(q => q.Category).ThenBy(q => q.Filename).ToList().AsReadOnly();
}
```

This eliminates the three duplicated blocks and makes adding a new source (JSON, YAML, API) a one-line registration.

## 20. `BATCHSIZE = 1` – Performance Anti-Pattern

**Where:** `EmbedTextPipeline`

```csharp

```

This means one HTTP call to the embedding API per document. For a repo with thousands of files, this is extremely slow.

**Fix:** Make it configurable (see #7) and set a sensible default (e.g., 16 or 32). Add a rate-limit / Polly retry policy around the embedding calls.
