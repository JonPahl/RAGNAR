## 1. `NumberedRowDecorator.Render()` — Row Duplication Bug

**Impact: HIGH (correctness) · Effort: LOW (~15 min)**

```csharp
// Current (broken) logic:
var existing = table.Rows.Select(r => r.ToArray()).ToList();
for (var i = 0; i < existing.Count; i++)
{
    // ... builds indexed[[]] ...
    table.AddRow(row);          // ← ADDS a new row; never removes the original
}
inner.Render();                 // ← renders original rows + numbered duplicates
```

The comment `// ← replace, don't add` even acknowledges the intent, but the code calls `table.AddRow(row)`, which *appends*. Every invocation of this decorator doubles the row count in the console table. The original (un-numbered) rows remain, followed by a second copy with the `#` index column. This is a **deterministic, user-visible correctness bug** — it does not depend on timing or environment.

**Remediation (sketch):**

```csharp
public void Render()
{
    if (_numbered) { inner.Render(); return; }
    _numbered = true;

    var table = inner.Table;
    if (!table.Columns.Contains(columnHeader, StringComparer.OrdinalIgnoreCase))
        table.AddColumns(columnHeader);

    // Snapshot → clear → re-insert with index column
    var snapshot = table.Rows.Select(r => r.ToArray()).ToList();
    table.Rows.Clear();                          // or however ConsoleTableBuilder exposes removal
    for (var i = 0; i < snapshot.Count; i++)
    {
        var cells = new string[[table.Columns.Count]];
        cells[[0]] = (i + 1).ToString();
        Array.Copy(snapshot[[i]], 0, cells, 1, snapshot[[i]].Length);
        table.AddRow(cells.Select(c => new TableCell(c)).ToList());
    }
    inner.Render();
}
```

## 2. `PipelineRunner.ReplaceStage` — Compound Race Condition

**Impact: HIGH (data-corruption / pipeline integrity) · Effort: MEDIUM (~1 hr)**

```csharp
public IPipeline<TContext> ReplaceStage(string oldName, IPipelineStage<TContext> newStage, IAsyncPolicy? policy = null)
{
    // ❌ Read is UNLOCKED — another thread can mutate _stages between these two lines
    var oldIdx = _stages.IndexOf(_stages.Find(x => x.PipelineStage.Name == oldName));
    if (oldIdx == -1) throw new KeyNotFoundException();

    RemoveStage(oldName);   // acquires lock, removes, releases lock
    AddStage(newStage, policy);  // acquires lock, appends to END, releases lock
    return Reorder(newStage.Name, oldIdx); // acquires lock, moves, releases lock
}
```

Three distinct problems:

| # | Issue | Consequence |
|---|-------|-------------|
| a | `IndexOf`/`Find` run **outside** `_gate` | A concurrent `ClearStages()` or `AddStage` can change the list between the read and the first lock → `oldIdx` is stale, `Reorder` throws `KeyNotFoundException` or moves the wrong entry. |
| b | `RemoveStage` and `AddStage` are **separate lock acquisitions** | A concurrent `AddStage` can insert a stage *between* the remove and the add, so the new stage lands at the **end** instead of the original position. |
| c | `Reorder` is a **third** lock acquisition | A concurrent `RemoveStage` can delete the stage that was just added, leaving the pipeline in an inconsistent state. |

This is not merely a style issue — it can silently reorder or lose stages in a multi-threaded hosting scenario (e.g., DI scope disposal racing a pipeline rebuild).

**Remediation (sketch):**

```csharp
public IPipeline<TContext> ReplaceStage(string oldName, IPipelineStage<TContext> newStage, IAsyncPolicy? policy = null)
{
    lock (_gate)
    {
        var oldIdx = _stages.FindIndex(x => x.PipelineStage.Name == oldName);
        if (oldIdx == -1) throw new KeyNotFoundException(oldName);
        _stages[[oldIdx]] = new StageEntry<TContext>(newStage, policy); // atomic swap
    }
    return this;
}
```

One lock, one read, one write. No TOCTOU window.

## 3. `QuestionFilterSelector` — DI Bypass + Silent Empty-Filter Fallback

**Impact: MEDIUM-HIGH (wrong query results / untestable) · Effort: LOW-MEDIUM (~30 min)**

```csharp
public QuestionFilterSelector(Serilog.ILogger logger, IEnumerable<IFilterStrategy> strategies)
{
    _strategies = strategies.ToDictionary(s => s.SupportedCategory);

    // ❌ Hand-rolled "registration" that bypasses the DI container
    if (!_strategies.ContainsKey(QuestionCategory.XML))
        _strategies[[QuestionCategory.XML]] = new XmlCommentFilterStrategy(logger);
}

public Filter FindFilter(QuestionCategory category, int commentLengthThreshold = 0)
{
    // ❌ Silent fallback: unknown category → empty Filter (no conditions)
    var filter = _strategies.TryGetValue(category, out var strategy)
        ? strategy.CreateFilter(commentLengthThreshold)
        : new Filter();          // ← zero must, zero mustNot → Qdrant returns EVERYTHING
    return filter;
}
```

Three compounding problems:

1. **DI bypass.** `XmlCommentFilterStrategy` is instantiated with `new` instead of being resolved from the container. If a test or a downstream module replaces `IFilterStrategy` registrations, this hidden instance silently wins, making the behaviour impossible to predict or override.

2. **Silent empty-filter fallback.** When a category has no registered strategy (e.g., `QuestionCategory.Uncategorized`), `FindFilter` returns `new Filter()` with **zero conditions**. Qdrant interprets an empty filter as "match all points." The RAG pipeline then feeds irrelevant code chunks into the LLM prompt, degrading answer quality with no log entry and no exception.

3. **OCP violation.** Adding a new question category requires editing this class (or relying on the DI-registered strategy being present). The "register built-in strategies ONCE" comment in the source is misleading — the class is registered as a **singleton**, but the `new` call is still a code-level coupling that resists extension.

**Remediation (sketch):**

```csharp
// In DI (Program.cs / setup):
services.AddSingleton<IFilterStrategy>(sp =>
    new XmlCommentFilterStrategy(sp.GetRequiredService<ILogger>()));

// In QuestionFilterSelector — remove the manual new:
public QuestionFilterSelector(ILogger logger, IEnumerable<IFilterStrategy> strategies)
{
    _strategies = strategies.ToDictionary(s => s.SupportedCategory);
}

public Filter FindFilter(QuestionCategory category, int commentLengthThreshold = 0)
{
    if (!_strategies.TryGetValue(category, out var strategy))
        throw new NotSupportedException(
            $"No IFilterStrategy registered for {category}. " +
            $"Available: {string.Join(", ", _strategies.Keys)}.");
    return strategy.CreateFilter(commentLengthThreshold);
}
```

Fail fast at the boundary, keep all strategy creation inside the container, and make "unknown category" a visible, testable error rather than a silent match-all.
