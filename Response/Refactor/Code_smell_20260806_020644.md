## Code Smells Identified

### 1. **Duplicate Test Classes**
Multiple test classes with identical names but different implementations:
- `QuestionExtensionsTests` appears multiple times with conflicting test implementations
- `QuestionExtensionsToActiveOrDisabledTests` appears twice identically
- `StringExtensionsTests` and other test classes show duplication

**Fix:**
- Consolidate duplicate test classes into single, comprehensive test classes
- Use parameterized tests instead of multiple similar test methods
- Remove redundant test files

### 2. **Inconsistent Test Naming Conventions**
Tests use different naming patterns:
- `ActiveOnly_ReturnsOnlyEnabledQuestions` vs `ActiveOnlyReturnsOnlyEnabledQuestions`
- `WhereCategoryIs_FiltersByCategories` vs `MatchesCategories_ReturnsFilteredQuestions`

**Fix:**
- Standardize naming convention (e.g., `MethodName_StateUnderTest_ExpectedBehavior`)
- Use consistent patterns across all test classes

### 3. **Overly Complex Test Methods**
Some test methods are too long and test multiple scenarios:
- Tests that verify multiple assertions without clear separation
- Mixed concerns in single test methods

**Fix:**
- Split complex tests into smaller, focused tests
- Each test should verify one specific behavior
- Use `Theory` and `InlineData` for parameterized testing

### 4. **Magic Numbers and Hardcoded Values**
```csharp
var Questions = new List<Question>
{
    new(true, "Q1", "f1.cs", QuestionCategory.XML),
    new(false, "Q2", "f2.cs", QuestionCategory.General),
    // ...
};
```

**Fix:**
- Extract test data to separate factory methods or data builders
- Use meaningful variable names instead of "Q1", "Q2"
- Create test data builders for complex object creation

### 5. **Incomplete Test Coverage**
Some test methods have incomplete assertions:
```csharp
[Fact]
public void ApplyFilter_CallsCorrectStrategy(bool IsEnabled)
{
    // ...
    // Note: actual strategy behavior depends on internal implementation
}
```

**Fix:**
- Complete all test assertions
- Verify actual behavior, not just that methods are called
- Use mocking frameworks appropriately

### 6. **Tight Coupling in Test Setup**
Tests directly instantiate complex objects without abstraction.

**Fix:**
- Use dependency injection for test dependencies
- Create test-specific factories or builders
- Mock external dependencies

### 7. **Inconsistent Error Handling in Tests**
Some tests expect specific exception messages, others don't:
```csharp
Assert.Throws<ArgumentException>(() => Question.ValidateQuestion());
// vs
Act.Should().Throw<ArgumentException>().WithMessage($"*{expectedMessage}*");
```

**Fix:**
- Standardize exception assertion patterns
- Always verify exception messages when relevant
- Use consistent assertion libraries (FluentAssertions vs MSTest)

### 8. **Redundant Test Scenarios**
Multiple tests covering the same edge cases:
- Several tests for null/empty string validation
- Duplicate tests for disabled question handling

**Fix:**
- Remove redundant tests
- Focus on unique scenarios and edge cases
- Use combinatorial testing for complex parameter combinations

## Recommended Refactoring Approach

1. **Consolidate duplicate test classes** first
2. **Standardize naming conventions** across the test suite
3. **Create test data builders** for common object creation patterns
4. **Implement comprehensive mocking** for dependencies
5. **Add missing assertions** to incomplete tests
6. **Remove redundant tests** while maintaining coverage

**After:**
```csharp
[Theory]
[InlineData(true, 1)]
[InlineData(false, 0)]
public void ActiveOnly_ReturnsOnlyEnabledQuestions(bool isEnabled, int expectedCount)
{
    // Arrange
    var questions = new[]
    {
        CreateQuestion(isEnabled: isEnabled),
        CreateQuestion(isEnabled: !isEnabled),
        CreateQuestion(isEnabled: isEnabled)
    }.ToImmutableList();
    
    // Act
    var active = questions.ActiveOnly();
    
    // Assert
    active.Should().HaveCount(expectedCount)
        .And.AllBeOfType<Question>()
        .And.OnlyContain(q => q.IsEnabled == isEnabled);
}

private Question CreateQuestion(bool isEnabled, string text = "Test", 
    string filename = "test.cs", QuestionCategory category = QuestionCategory.XML)
    => new Question(isEnabled, text, filename, category);
```

This approach reduces duplication, improves readability, and makes tests more maintainable.
