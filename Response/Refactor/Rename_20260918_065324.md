# Naming Recommendations for Ragnar

Below is a structured set of renaming suggestions grouped by area of concern. Each entry shows the **current name**, the **recommended name**, and a short rationale.

---

## 1. The `IQuestionEmbedding` Interface (Most Misleading Name)

| Current | Recommended | Why |
|---|---|---|
| `IQuestionEmbedding` | `IContextRetriever` | The interface has nothing to do with *embedding* (generating vectors). Its sole method is `RetrieveContextAsync`, which performs a vector **search**. The name misleads readers into thinking it generates embeddings. |
| `IQuestionEmbedding.RetrieveContextAsync` | `IContextRetriever.RetrieveAsync` | Drop the redundant "Context" from the method (the interface already says "Context"). `RetrieveAsync` reads more naturally. |
| `IEmbeddingService` (in `OllamaEmbeddingService`) | keep as-is | This one *does* generate embeddings, so the name is correct. The contrast between the two is the problem. |

**Impact on `QuestionExecutionStage` constructor:** the parameter currently typed `IQuestionEmbedding` becomes `IContextRetriever`, immediately making it obvious the stage *retrieves* context rather than *embeds* something.

## 2. The Two Confusing "Writer" / "Output" Interfaces

Right now there are three overlapping names:

| Current | Recommended | Rationale |
|---|---|---|
| `IOutputWriter` (console) | `IConsoleWriter` | "Output" is ambiguous—file output? console output? "Console" is unambiguous. |
| `IWriter` (file I/O) | `IFileWriter` | Matches the existing implementation class `FileWriter`. "Writer" alone is too generic in a codebase that also has `ResponseWriter`, `CsvFileQuestionProvider`, etc. |
| `IResponseWriter` / `ResponseWriter` | keep as-is | Already clear once `IWriter` → `IFileWriter` resolves the collision. |

**Impact:** `PipelineRunner(IOutputWriter writer, …)` → `PipelineRunner(IConsoleWriter writer, …)` makes the constructor self-documenting.

## 4. `IQuestionSourceBuilder` – Fluent API

The current chain `GetCategories().GetFileConfig().GetCsvFilesAsync(…).WithCategoryFilter().Build()` mixes **Get** (imperative "fetch") and **With** (configurative "set") verbs inconsistently.

| Current | Recommended | Why |
|---|---|---|
| `IQuestionSourceBuilder` | `IQuestionCollectionBuilder` | "Source" is ambiguous (file source? data source?). "Collection" matches the return type. |
| `GetCategories()` | `WithCategories(params QuestionCategory[[]] cats)` | "With" = configure a parameter. "Get" implies returning data. |
| `GetFileConfig()` | `WithFileConfiguration(FileLoadOptions cfg)` | Same verb consistency. |
| `GetCsvFilesAsync(dir, ct)` | `LoadQuestionsFromDirectoryAsync(dir, ct)` | The method doesn't return files; it triggers loading. |
| `WithCategoryFilter()` | `FilterByCategory()` | "With" + "Filter" is redundant. |
| `Build()` | `BuildQuestions()` | `Build()` is too generic for a builder that also does I/O. |

Revised chain reads as:
```csharp
builder
    .WithCategories(QuestionCategory.CSharp, QuestionCategory.XML)
    .WithFileConfiguration(fileOpts)
    .FilterByCategory()
    .await LoadQuestionsFromDirectoryAsync(pluginDir, ct)
    .BuildQuestions();
```

## Summary of Highest-Impact Renames

If you only have time for a few changes, these five will eliminate the most confusion:

1. **`IQuestionEmbedding` → `IContextRetriever`** – removes the single most misleading name in the codebase.
2. **`IOutputWriter` → `IConsoleWriter`** and **`IWriter` → `IFileWriter`** – eliminates the three-writer collision.
3. **`QuestionExecutionStage` → `QuestionAnsweringStage`** (and its test) – aligns class, display name, and test.
4. **`VectorStoreBuilder` → `VectorStoreManager`** – a "builder" that only checks existence is a source of confusion.
5. **`IQuestionSourceBuilder` fluent verbs** – unify `Get*` / `With*` into a consistent `With*` / `Load*` / `BuildQuestions` pattern.
