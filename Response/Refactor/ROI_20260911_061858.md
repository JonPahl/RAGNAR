## 1. Invalid `extension(...)` Syntax (Compilation Blocker)

**Impact: CRITICAL — the code will not compile**
**Effort: HIGH — systemic across 4+ classes**

Four classes use a non-existent C# keyword `extension(...)` to wrap methods:

| File | Line(s) affected |
|------|-----------------|
| `ApplicationConfigurationExtensions` | `extension(IServiceCollection services)` |
| `StringExtensions` | `extension(ReadOnlySpan<char> value)` |
| `AssemblyExtensions` | `extension(Assembly asm)` |
| `StylesExtensions` | `extension(Style? style)` |

C# has no `extension` keyword. Extension methods are declared as `public static` methods inside a `static class` with a `this` modifier on the first parameter. As written, every one of these files is a compile error, which means the entire solution is non-buildable.

**Why it's #1:** No feature ships, no tests run, nothing is deployable. This gates every other concern.

**Remediation sketch (one example, the same pattern applies to all four):**

```csharp
// BEFORE (invalid)
public static class ApplicationConfigurationExtensions
{
    extension(IServiceCollection services)
    {
        public IServiceCollection RegisterEmbeddingServices() { … }
    }
}

// AFTER (valid C#)
public static class ApplicationConfigurationExtensions
{
    public static IServiceCollection RegisterEmbeddingServices(this IServiceCollection services) { … }

    public static IServiceCollection LoadQuestionPlugins(this IServiceCollection services) { … }
}
```

Each method must become a top-level `public static` method with `this` on the first parameter. The `IReadOnlySpan<char>` and `Assembly` extensions follow the same pattern. Estimate: 6–10 methods to restructure plus a full compile-and-fix cycle.

## 2. `OllamaChatResponse` – Closure Capture Bug in Live-Render Loop

**Impact: HIGH — the primary user-facing operation (response generation) renders incorrectly**
**Effort: MEDIUM — restructure one class's rendering pipeline**

In `OllamaChatResponse.GenerateResponse`, the `Panel` and `PanelHeader` are constructed **before** the `AnsiConsole.Live` loop, capturing `headerText` and `panelText` by reference:

```csharp
var headerText = new PanelHeader(" Generating... ");   // captured here
var panelText  = new Markup(string.Empty, Styles.Yellow).LeftJustified();
var panel      = new Panel(panelText).Header(headerText)
                 .BorderColor(Color.Green).RoundedBorder()
                 .BorderStyle(Styles.GreenBlink).Expand().Padding(1,1,1,1);

// Inside the Live loop:
client.OnThink += (sender, token) =>
{
    headerText = new PanelHeader("Thinking");          // ← NEW object
    panelText  = new Markup(thinkingText.ToString(), Styles.Red); // ← NEW object
    ctx.UpdateTarget(panel);   // panel still holds the ORIGINAL panelText
    ctx.Refresh();
};
```

Reassigning `headerText` / `panelText` creates **new** objects, but the `Panel` was already wired to the **original** instances. The "Thinking" label and the red thinking text will never appear. The same issue affects the streaming loop that reassigns `panelText` for each token.

Additionally, `throw new ArgumentException("null response is null")` should be `ArgumentNullException` (or an `InvalidOperationException`), and the `try/catch` wrapping synchronous property-set + event-subscription is misleading.

**Remediation:** Use a single mutable `Markup` instance (or a `StringBuilder` + `Markup` pair) and mutate it in place via `ctx.UpdateTarget`. Alternatively, build the panel fresh each tick inside the loop. Remove the misleading `try/catch` around synchronous setup.

## 3. `VectorStoreRepository` – Per-Document Embedding + Upsert (No Batching)

**Impact: HIGH — linear degradation with codebase size; a 5,000-file repo means 5,000 sequential Ollama round-trips + 5,000 Qdrant gRPC calls**
**Effort: MEDIUM — rework one method + the pipeline caller**

`EmbedTextPipeline` chunks documents into `BATCHSIZE = 32` and calls `repository.UpsertBatchAsync(batch, ct)`. But inside `VectorStoreRepository`:

```csharp
public async Task<UpdateResult> UpsertBatchAsync(CodeDocument[[]] codeDocuments, CancellationToken ct)
{
    foreach (var doc in codeDocuments)          // ← sequential, one at a time
    {
        var vector = await embeddingService.GenerateAsync(text, ct);   // 1 HTTP call
        await qdrantClient.UpsertAsync(name, points, ct: ct);         // 1 gRPC call
    }
}
```

Despite the method name and the caller's batching, **no actual batching occurs**. For a 3 200-document corpus this is ~3 200 × (embed-latency + upsert-latency) with zero concurrency. The `IEmbeddingService.GenerateBatchAsync` method already exists and accepts `IReadOnlyCollection<string>`, yet is never called.

**Remediation:**

1. Collect all `CodeDocument`s for the batch.
2. Call `embeddingService.GenerateBatchAsync(allTexts, ct)` once.
3. Zip results back to documents, build all `PointStruct`s in memory.
4. Call `qdrantClient.UpsertAsync(collectionName, allPoints, ct)` once.
5. Return a single `UpdateResult`.

This turns N sequential round-trips into 2 (one embed, one upsert) per batch, matching the intent of `BATCHSIZE = 32` and the existing batch API.
