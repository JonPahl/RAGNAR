## 1. `QdrantFilterBuilder.Build()` — Internal List Aliasing (Correctness Bug)

**Location:** `QdrantFilterBuilder.cs`, `Build()` method

**The problem:**

```csharp
public Filter Build()
{
    // …
    return new Filter
    {
        Must    = { _must },      // ← same List<Condition> reference
        MustNot = { _mustNot },   // ← same List<Condition> reference
        Should  = { _should }     // ← same List<Condition> reference
    };
}
```

The returned `Filter` object **shares the same `List<Condition>` instances** as the builder's private fields. Any subsequent call to `AddMatch`, `AddRange`, `Clear`, or even `AddExceptKeywords` on the same builder **mutates every previously-built `Filter` in place**. Because `Filter` is typically handed to the Qdrant client and may be held by other services, this produces **silently wrong query results** with no exception, no log, and no observable failure—exactly the class of bug that is hardest to diagnose in production.

A concrete failure path:

```csharp
var builder = new QdrantFilterBuilder();
builder.AddMatch("Category", "XML");
var f1 = builder.Build();          // f1.Must points at builder._must

builder.AddRange("Len", 50, 500); // mutates builder._must
// f1.Must now contains BOTH conditions — the caller never asked for that.
```

**Impact:** Incorrect vector-search filters → wrong code-document retrieval → wrong LLM answers. In a RAG pipeline this is a data-integrity defect, not a crash.

**Remediation (low effort, ~15 min):**

```csharp
public Filter Build()
{
    if (IsEmpty)
        throw new InvalidOperationException("…");

    return new Filter
    {
        Must    = [[.. _must]],       // materialised copies
        MustNot = [[.. _mustNot]],
        Should  = [[.. _should]]
    };
}
```

Optionally make the lists `ReadOnlyCollection` after `Build()` to enforce immutability at the type level.

## 2. `CodeParserFactory` — Single-Extension Assumption (Functional Bug)

**Location:** `CodeParserFactory.cs`, constructor

**The problem:**

```csharp
private readonly Dictionary<string, IFileParser> _byExt =
    parsers.ToDictionary(p => p.SupportedExtensions[[0]], StringComparer.OrdinalIgnoreCase);
```

Only **the first element** of each parser's `SupportedExtensions` list is registered. The `IFileParser` contract explicitly declares `IList<string> SupportedExtensions`, implying a parser can handle multiple extensions (e.g., a C# parser registering both `.cs` and `.csx`, or a Markdown parser registering `.md` and `.mdx`). Any file whose extension is **not** the first one silently falls through to the hardcoded Markdown fallback:

```csharp
if (!_byExt.TryGetValue(ext, out var parser))
{
    parser = new MarkdownFileParser(options, logger);   // ← wrong parser for .csx, .csproj, etc.
}
```

**Impact:** Files are parsed by the wrong parser, producing garbage `CodeDocument` segments. The downstream embedding and vector-store steps then index **incorrect representations** of the source, degrading retrieval quality for every query that touches those files. Because no exception is thrown, the pipeline appears healthy.

**Remediation (low–moderate effort, ~30 min):**

```csharp
private readonly Dictionary<string, IFileParser> _byExt;

public CodeParserFactory(ILogger logger, IOptions<RagnarConfig> options, IEnumerable<IFileParser> parsers)
{
    _logger = logger;
    _options = options;
    _fallback = new MarkdownFileParser(options, logger);
    _byExt = new Dictionary<string, IFileParser>(StringComparer.OrdinalIgnoreCase);

    foreach (var parser in parsers)
    {
        foreach (var ext in parser.SupportedExtensions)
            _byExt[[ext]] = parser;            // every extension maps to the right parser
    }
}
```

Also add a `SupportedExtensions` guard (non-null, non-empty) to the `IFileParser` implementations or at DI-registration time so a misconfigured parser fails fast.

## 3. `FileDiscoveryService.GetFilesAsync` — Synchronous Blocking I/O in an Async Method (Scalability / Responsiveness)

**Location:** `FileDiscoveryService.cs`, `GetFilesAsync`

**The problem:**

```csharp
public async IAsyncEnumerable<string> GetFilesAsync(
    string directory, IOptions<RagnarConfig> options,
    [[EnumeratorCancellation]] CancellationToken cancellationToken)
{
    // …
    foreach (var path in Directory.EnumerateFiles(directory, "*.*", SearchOption.AllDirectories))
    //                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^^  synchronous, blocking, recursive
    {
        cancellationToken.ThrowIfCancellationRequested();
        // …
        yield return path;
        await Task.Yield();          // yields AFTER the blocking call, not before
    }
}
```

Two distinct issues compound:

| Issue | Consequence |
|---|---|
| `Directory.EnumerateFiles(…, SearchOption.AllDirectories)` performs **synchronous recursive I/O** on the calling thread. On a large repository (tens of thousands of files across nested `node_modules`, `.git`, etc.) this can block for **seconds to minutes**. | The calling thread is held. In a generic-host background service this starves the thread-pool; in a Web API handler it blocks a request thread. |
| `await Task.Yield()` is placed **after** `yield return`, so it only releases the thread once a file has already been enumerated. The initial enumeration loop (which does the real disk I/O) is never offloaded. | The method's `async` / `IAsyncEnumerable` contract is **misleading**—consumers believe the operation is non-blocking, but the dominant cost is synchronous. |

**Impact:** On a monorepo-scale scan the pipeline stalls at the discovery stage. Because the `PipelineRunner` executes stages sequentially, every downstream stage (parsing, embedding, upsert) is delayed. Under concurrent pipeline invocations this scales linearly with thread-pool exhaustion rather than with available I/O parallelism.

**Remediation (moderate effort, ~1–2 hr):**

```csharp
// .NET 7+
await foreach (var path in Directory.EnumerateFilesAsync(
    directory, "*.*", SearchOption.AllDirectories, cancellationToken))
{
    var fi = new FileInfo(path);
    if (!validator.IsValid(fi, filter)) { skippedCount++; continue; }

    discoveredCount++;
    logger.LogDebug("Eligible file: {Path}", path);
    yield return path;
}
```

If targeting .NET 6 or earlier, wrap the enumeration in `Task.Run` and buffer results into a `Channel<string>`, then `await foreach` over the channel's `Reader`. Either way, add a **max-depth** or **excluded-directory** filter (the `FileLoadOptions.ExcludedDirectories` field exists but is never consulted here) to prune `bin/`, `obj/`, `node_modules/`, `.git/` before the OS walk, cutting the file count by orders of magnitude.
