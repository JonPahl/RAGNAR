### 🔍 1. Tight Coupling & Magic Strings in Qdrant Integration
**Location:** `ConfigurationBasedQuestionLoader`, `QuestionEmbedding`  
**Problem:** Complex gRPC/protobuf types (`Filter`, `Condition`, `FieldCondition`, etc.) are instantiated inline, and payload keys like `"Comment_Length"`, `"file_name"`, `"Code"` are hardcoded strings. This makes the code brittle, hard to test, and tightly coupled to Qdrant's internal schema.
**Impact:** Schema changes in Qdrant require widespread refactoring. Unit testing becomes difficult due to heavy concrete dependencies.
**Fix:**
- Extract filter construction into a dedicated builder/factory: `QdrantFilterBuilder`
- Use strongly-typed constants or records for payload mapping instead of raw strings.
```csharp
// Before (inline & magic strings)
var filter = new Filter { Should = { new Condition { Field = new FieldCondition { Key = "Comment", Match = new Match { Text = "" } } } } };

// After (decoupled & type-safe)
public static class QdrantFilterKeys
{
    public const string Comment = nameof(CodeDocument.Comment);
    // ...
}

var filter = FilterBuilder.CreateEmptyCommentFilter();
```

### 📦 2. Violation of SRP & OCP in `ConfigurationBasedQuestionLoader`
**Location:** `LoadFromConfig` method  
**Problem:** The method handles configuration loading, category branching (`if (question.Category == QuestionCategory.XML)`), filter application, and collection building. Adding a new category requires modifying this class.
**Impact:** Violates Single Responsibility Principle (SRP) and Open/Closed Principle (OCP). Becomes a "god method" as the project scales.
**Fix:** Extract category-specific logic into strategies or use a configuration-driven approach:
```csharp
// Strategy interface
public interface IQuestionFilterStrategy
{
    Filter? GetFilter(Question question);
}

// Registration
var strategies = new Dictionary<QuestionCategory, IQuestionFilterStrategy>
{
    { QuestionCategory.XML, new XmlCommentFilterStrategy() },
    // ...
};

// In LoadFromConfig
var filter = strategies.TryGetValue(question.Category, out var strategy) 
    ? strategy.GetFilter(question) 
    : null;
```

### 🔀 3. Fragmented & Inconsistent API Design in `QuestionExtensions`
**Location:** Two separate `QuestionExtensions` classes/methods provided  
**Problem:** One extension class handles querying (`ActiveOnly`, `InActiveOnly`, `WithCategory`), while another handles mutation/validation (`SetFilter`, `ValidateQuestion`). This splits related functionality and creates API confusion. Additionally, `ValidateQuestion` uses reflection to inspect properties, which is slow and fragile.
**Impact:** Developers must search multiple files for question-related operations. Reflection-based validation breaks easily with renaming or structural changes.
**Fix:**
- Consolidate into a single extension class or split by clear concern: `QuestionQueryExtensions` vs `QuestionValidationExtensions`.
- Replace reflection with explicit checks or a dedicated validator using `System.ComponentModel.DataAnnotations` or FluentValidation.
```csharp
// Explicit validation (fast & refactor-safe)
public static Question Validate(this Question q) => new(
    q.IsEnabled,
    Guard.Against.NullOrWhiteSpace(q.Text),
    Guard.Against.NullOrWhiteSpace(q.Filename),
    q.Category
);
```
