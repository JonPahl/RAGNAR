## 1. `VectorStoreRepository.UpsertBatchAsync` — Premature `return` Silently Drops Data

**Severity: Critical (functional bug)** | **Remediation: Trivial**

```csharp
public async Task<UpdateResult> UpsertBatchAsync(CodeDocument[[]] codeDocuments, CancellationToken cancellationToken)
{
    foreach (var doc in codeDocuments)
    {
        // ... generate embedding, build points ...
        try
        {
            return points.Count > 0 
                ? await qdrantClient.UpsertAsync(...) 
                : new UpdateResult { Status = UpdateStatus.UnknownUpdateStatus };
            // ^^^ RETURNS HERE — loop body never continues past the first doc
        }
        // ...
    }
    return new UpdateResult { Status = UpdateStatus.Completed };
}
```

**Impact:** Only the **first** document in every batch is ever upserted into Qdrant. All subsequent documents in the array are silently discarded. Since `EmbedTextPipeline` calls this with `BATCHSIZE = 1` the symptom is masked today, but the moment batch size increases (or another caller passes a real array), the vector store will be catastrophically incomplete. RAG retrieval quality degrades proportionally to the number of lost chunks.

**Remediation (~15 min):**
- Remove the `return` from inside the `foreach`.
- Accumulate the last (or all) `UpdateResult` and return after the loop.
- Consider using Qdrant's native multi-point upsert (`qdrantClient.UpsertAsync(collection, allPoints)`) to eliminate per-document HTTP round-trips entirely.

## 2. `BATCHSIZE = 1` in `EmbedTextPipeline` — Sequential Single-Document Embedding

**Severity: High (performance)** | **Remediation: Low–Medium**

```csharp
private const int BATCHSIZE = 1;
// ...
foreach (var batch in documents.Chunk(BATCHSIZE))   // every "batch" is 1 element
{
    await repository.UpsertBatchAsync(batch, ct);  // 1 HTTP call per document
}
```

**Impact:** For a mid-size C# solution (200+ source files), this produces **200+ sequential HTTP round-trips** to the Ollama embedding endpoint plus **200+ sequential Qdrant upserts**. At ~50–200 ms per round-trip, total indexing time stretches to **30–60+ seconds** where a properly batched implementation would finish in **2–5 seconds**. This makes iterative re-indexing during development impractical and scales linearly with codebase size.

**Remediation (~1–2 hrs):**
| Change | Detail |
|--------|--------|
| Raise `BATCHSIZE` | `32` or `64` (tune against model context window) |
| True batch upsert | In `VectorStoreRepository`, collect all `PointStruct[[]]` from the batch and call `qdrantClient.UpsertAsync` **once** with the combined list |
| Parallelise embedding | `Parallel.ForEachAsync` with `MaxDegreeOfParallelism = 4` over chunks (embedding calls are I/O-bound) |
| Remove dead code | Delete the ~30 lines of commented-out `AnsiConsole.Progress` block and the TODO |

## 3. Swallowed Exception in `OllamaChatResponse` Thinking Handler

**Severity: Medium (silent data loss / misleading UX)** | **Remediation: Trivial**

```csharp
client.OnThink += (sender, token) =>
{
    headerText = new PanelHeader("Thinking");
    var clean = Markup.Escape(token);
    thinkingText.Append(clean);
    panelText = new Markup(thinkingText.ToString(), Styles.Red);
    ctx.UpdateTarget(panel);
    ctx.UpdateTarget(panelText);
    ctx.Refresh();
};
// ...
catch (Exception ex)
{
    var y = ex.Message;   // ← exception swallowed; user sees nothing
}
```

**Impact:** If the Ollama thinking-token stream throws (network blip, model OOM, malformed token), the exception is **entirely discarded**. The user's live panel freezes mid-think with no error message, no retry, and no log entry. The method then continues into `SendAsAsync`, potentially rendering a **partial or empty answer** that looks plausible. In a RAG tool whose value proposition is correctness of code recommendations, silently truncated responses are dangerous.

**Remediation (~10 min):**
```csharp
catch (Exception ex) when (ex is not OperationCanceledException)
{
    _logger?.Error(ex, "Thinking stream failed: {Msg}", ex.Message);
    completeText.Append($"\n\n[[ERROR]] Thinking stream interrupted: {ex.Message}\n");
    // Optionally re-throw or mark the response as degraded
}
```
Also inject an `ILogger` into `OllamaChatResponse` (currently has no logging dependency at all) so the failure is observable in Seq/file sinks.
