## Recommended Feature: Incremental Indexing with Content-Hash Caching

After reviewing the full codebase, the most impactful feature to add would be **incremental (delta) indexing** — the ability to detect which file segments have actually changed since the last run and re-embed only those, rather than regenerating every embedding on every execution.

### Why this matters

The current pipeline (`FileDiscoveryService` → `CodeParserFactory` → embedding → `VectorStoreWriter.UpsertBatchAsync`) performs a full re-embed on every run. The embedding step is by far the most expensive operation (network round-trips to Ollama, batched at `EmbeddingOptions.BatchSize`). For a mid-sized C# solution with thousands of parsed segments, re-running after a one-line change forces the user to wait for all segments to be re-embedded, even though 99.9% of them are identical to what's already in Qdrant.

### Sketch of the design

```
┌─────────────────────────────────────────────────────────────────┐
│  Pipeline (existing)                                            │
│                                                                 │
│  FileDiscovery → Parse → [[NEW: HashCheck]] → Embed → Upsert     │
└─────────────────────────────────────────────────────────────────┘
```

1. **Add a deterministic content hash** to `CodeDocument` (e.g., SHA-256 of `Code` + `Comment` + `ElementType` + `ElementName`). Store it as a Qdrant payload field (`ContentHash`).

2. **New stage: `SegmentDeltaStage`** (between parsing and embedding):
   - For each parsed `CodeDocument`, compute its hash.
   - Query Qdrant for existing points whose `FilePath` + `ContentHash` match.
   - Partition the document list into `unchanged` (skip) and `changed` / `new` (proceed to embedding).
   - Delete Qdrant points whose `FilePath` matches a file that no longer exists or whose hash no longer matches (handles renames and deletions).

3. **Extend `VectorStoreWriter`** with a `PruneStaleAsync(string filePath, IReadOnlyCollection<string> currentHashes)` method that removes orphaned points.

4. **Log a summary** in the timing middleware:
   ```
   Stage [[3/5]] Embedding completed in 1.24s (7 of 1,204 segments re-embedded, 1,197 cached)
   ```

### Minimal code additions (illustrative)

```csharp
// In CodeDocument
public string ContentHash { get; init; } = string.Empty;

// New stage
public sealed class SegmentDeltaStage(
    Serilog.ILogger logger,
    IQdrantClient qdrant,
    IOptions<RagnarConfig> options) : IPipelineStage<EmbeddingContext>
{
    public string Name => "Delta Check";
    public AsyncRetryPolicy? RetryPolicy => null;
    public bool ShouldRun(EmbeddingContext ctx) => true;

    public async Task ExecuteAsync(EmbeddingContext ctx, CancellationToken ct)
    {
        var all = ctx.Documents.ToList();
        var existing = await qdrant.RetrieveByPayloadAsync(
            options.Value.ApplicationOptions.VectorStoreName,
            filter: null, // fetch all hashes for the source directory
            ct);

        var seen = existing.Select(p => p.Payload[["ContentHash"]]?.ToString()).ToHashSet();
        ctx.Documents = all.Where(d => !seen.Contains(d.ContentHash)).ToList();
        ctx.SkippedCount = all.Count - ctx.Documents.Count;

        // Prune: delete points whose FilePath no longer appears in `all`
        var livePaths = all.Select(d => d.FilePath).ToHashSet();
        var stale = existing.Where(p => !livePaths.Contains(p.Payload[["FilePath"]]?.ToString())).ToList();
        if (stale.Count > 0)
            await qdrant.DeleteAsync(options.Value.ApplicationOptions.VectorStoreName,
                new Qdrant.Client.Models.Filter { MustNot = /* path not in livePaths */ }, ct);

        logger.Information("Delta: {ReEmbed} to embed, {Cached} unchanged, {Stale} pruned",
            ctx.Documents.Count, ctx.SkippedCount, stale.Count);
    }
}
```

### Secondary suggestions (smaller, high-value)

| Feature | Rationale |
|---|---|
| **`ragnar search "query"` CLI command** | The vector store + embedding service are already wired up; a direct top-k semantic search (no LLM round-trip) would make the tool useful for quick "where is this pattern used?" lookups without going through the question pipeline. |
| **`ragnar watch` mode** | Subscribe to `FileSystemWatcher` on `ApplicationOptions.SourceDirectory`; on change, re-run the pipeline (which, with incremental indexing, would only re-embed the touched segments). Great for active development. |
| **Diagnostics / health-check command** | A `ragnar doctor` that pings Ollama (`/api/version`), Qdrant (`/healthz`), verifies dimension match between `EmbeddingOptions.Dimension` and the live collection (`CollectionInfo.Dimension`), and reports config validity — saves debugging time when services are misconfigured. |

The incremental-indexing feature has the highest cost/benefit ratio: it's a ~200-line addition layered cleanly into the existing `PipelineRunner` / stage / middleware architecture, it eliminates the single biggest source of user friction (re-embed wait time), and it composes naturally with the other suggestions (watch mode, delta-aware pruning, etc.).
