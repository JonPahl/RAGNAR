# Performance Issues Identified in the Ragnar Codebase

## 1. O(n) Extension Lookup in `FileSystemEntryExtensions.HasAllowedExtension`

**Problem:** The method calls `allowedExtensions.Contains(...)` on an `IReadOnlyCollection<string>`. If the underlying collection is a `List<string>`, each call is O(n), and this is invoked **per file** during directory traversal.

**Fix:** Accept (or internally convert to) a `HashSet<string>` with `StringComparer.OrdinalIgnoreCase` for O(1) lookups.

```csharp
// In the caller that builds the filter, cache a HashSet once:
private static readonly HashSet<string> _allowedExts =
    new(config.AllowedFileExtensions, StringComparer.OrdinalIgnoreCase);

// Then the check becomes O(1):
public static bool HasAllowedExtension(this FileSystemEntry entry,
    HashSet<string> allowedExtensions)
{
    if (entry.IsDirectory) return false;
    return allowedExtensions.Contains(Path.GetExtension(entry.FileName)!);
}
```

## 2. Per-Row Console Refresh in `QuestionExecutionStage.ShowTable`

**Problem:** `AnsiConsole.Live(table).Start(ctx => …)` calls `ctx.Refresh()` after **every single row**. For a dataset of 5,000+ questions this forces thousands of full-screen repaints, which dominates wall-clock time.

**Fix:** Batch the refresh every N rows (or every ~50 ms) and do a final refresh:

```csharp
AnsiConsole.Live(table).AutoRefresh(false).Start(ctx =>
{
    for (var i = 0; i < questions.Count; i++)
    {
        table.AddRow(i.ToString(), questions[[i]].Category.ToString(), questions[[i]].Text);
        if ((i + 1) % 100 == 0 || i == questions.Count - 1)
            ctx.Refresh();
    }
});
```

Also consider removing the `Live` wrapper entirely and just building the table then calling `AnsiConsole.Write(table)` once—much faster for non-interactive output.

## 3. Redundant Filesystem Calls in `PathResolver` / `ResponseWriter`

**Problem:** For **every question response** the pipeline:
1. Calls `PathResolver.ResolveResponseDirectory` → `Directory.Exists(...)` (I/O syscall)
2. Calls `Directory.CreateDirectory(...)` (another I/O syscall)

With hundreds of questions this doubles the filesystem round-trips for the same directory.

**Fix:** Cache the resolved (and confirmed-created) directories in a `ConcurrentDictionary<string, string>`:

```csharp
public sealed class PathResolver(IOptions<RagnarConfig> options) : IPathResolver
{
    private static readonly ConcurrentDictionary<string, string> _cache = new();

    public string ResolveResponseDirectory(QuestionCategory? category)
    {
        var key = category?.ToString() ?? nameof(QuestionCategory.Uncategorized);
        return _cache.GetOrAdd(key, k =>
        {
            var responseDir = Path.Join(_appOpts.SourceDirectory, _appOpts.OutputFolder);
            Directory.CreateDirectory(Path.Join(responseDir, k)); // create once
            return Path.Join(responseDir, k);
        });
    }
}
```

## 4. Sequential Response Writing in `QuestionExecutionStage`

**Problem:** Each question's response is written to disk one-at-a-time. Since the writes are **independent I/O operations** (different files, different categories), they are serialized needlessly.

**Fix:** Parallelize with a bounded concurrency:

```csharp
await Parallel.ForEachAsync(questions,
    new ParallelOptions { MaxDegreeOfParallelism = 4, CancellationToken = ct },
    async (q, token) =>
{
    var path = await responseWriter.WriteResponseAsync(details, token);
    // …
});
```

## 5. `ConsoleTableBuilder` – Property Returns a Copy on Every Access

**Problem:**

```csharp
public List<string> Columns => [..Columns];   // allocates a new List every call
public List<string[[]]> Rows   => [..Rows];
```

Any hot loop that reads `builder.Columns.Count` or iterates `builder.Rows` allocates a fresh list per access, creating GC pressure.

**Fix:** Return the backing collection directly (or a `ReadOnlyCollection<T>` wrapper) and protect mutation through the builder API only:

```csharp
private readonly List<string> _columns = [];
private readonly List<string[[]]> _rows = [];

public IReadOnlyList<string> Columns => _columns;
public IReadOnlyList<string[]> Rows => _rows;
```

## 6. Duplicate `catch` Blocks in `PipelineRunner.ExecuteAsync`

**Problem (correctness + minor perf):**

```csharp
catch (OperationCanceledException) when (ct.IsCancellationRequested) { throw; }
catch (OperationCanceledException) when (ct.IsCancellationRequested) { throw; } // identical duplicate
```

The second block is dead code. While the JIT elides it, it signals a copy-paste bug and the extra condition evaluation on the first path is unnecessary.

**Fix:** Remove the duplicate.

## 7. Per-Call `CancellationTokenSource` Allocation in `OllamaEmbeddingService`

**Problem:** `CreateTimeoutCts` allocates a new `CancellationTokenSource` (and a timer) for **every** `GenerateAsync` / `GenerateBatchAsync` call. In a batch loop of thousands of documents this creates thousands of short-lived timers.

**Fix:** Reuse a single timeout CTS when the timeout value is constant (which it is, from config):

```csharp
private readonly CancellationTokenSource _timeoutCts = new() { };  // CancelAfter set once

public OllamaEmbeddingService(...)
{
    _timeoutCts.CancelAfter(config.Value.EmbeddingOptions.Timeout);
}

public async Task<ReadOnlyMemory<float>> GenerateAsync(string input, CancellationToken ct)
{
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(ct, _timeoutCts.Token);
    var result = await _generator.GenerateAsync(input, linked.Token);
    return result.Vector;
}
```

## 8. Unbounded Memory in `ShowTable` / `ConsoleTableBuilder`

**Problem:** All rows are accumulated in an in-memory `List<string[[]]>` before rendering. With 100k+ questions the table object graph can consume hundreds of MB.

**Fix:** For very large sets, stream the output in chunks (write 500-row tables, clear, repeat) or switch to a non-table console format (plain `writer.WriteLine`) with periodic progress.

## 9. Serilog Seq Sink – Unbounded Network Wait

**Problem:** The Seq sink (`http://localhost:5341`) has no explicit timeout/fallback in `appsettings.json`. If Seq is down, every log call can block on a TCP timeout (default ~30 s), stalling the pipeline.

**Fix:** Add a short timeout and an `OnSelfLog` handler, or gate the Seq sink behind a health-check / feature flag:

```json
{
  "Name": "Seq",
  "Args": {
    "serverUrl": "http://localhost:5341",
    "batchSizeLimit": 1000,
    "period": "00:00:02"
  }
}
```

And in code, wrap the Seq sink in a `try/catch` or use Serilog's `PeriodicBatchingSink` with a configurable timeout so a dead Seq never blocks the main thread.

## 10. `Parallel.ForEachAsync` Progress Contention in `ParsingStage`

**Problem:** Every thread calls `task.Increment(1)` on the shared Spectre progress task. Internally this takes a lock. With `MaxDegreeOfParallelism = 8` and many files, lock contention grows.

**Fix:** Accumulate locally and flush in batches:

```csharp
await Parallel.ForEachAsync(files, opts, async (filePath, token) =>
{
    var elements = await parseFactory.ParseAsync(filePath, token);
    documents.AddRange(elements);
});
task.Complete(files.Count);  // single update after all done
```

Or use `task.Increment(batchSize)` every N files.
