# Technical Debt Assessment

After a thorough review of the codebase, here is a categorised inventory of the technical debt I found, ordered roughly by severity.

---

## 1. Correctness Bugs

### 1.1 `EmbeddingGeneratorService` – timeout cancellation is swallowed
```csharp
timeoutCts.CancelAfter(configuration.Value.OllamaOptions.Timeout);
// ...
catch (OperationCanceledException) when (ct.IsCancellationRequested) { throw; }
catch (TimeoutException ex) { ... throw; }
```
When `CancelAfter` fires, the linked token is cancelled and `generator.GenerateAsync` throws `OperationCanceledException`. The `when (ct.IsCancellationRequested)` guard is **false** (the *user* token wasn't cancelled, only the timeout token was), so the first `catch` is skipped. The second `catch` looks for `TimeoutException`, but `CancelAfter` produces `OperationCanceledException`, **not** `TimeoutException`. The exception escapes both handlers and the `finally` disposes the CTS, leaving the caller with an unhandled `OperationCanceledException` and no diagnostic log.

**Fix:** either check `timeoutCts.IsCancellationRequested` in the `when` clause, or explicitly catch `OperationCanceledException` when `!ct.IsCancellationRequested` and wrap it in a `TimeoutException`.

### 1.2 `CodeParserFactory` – dead-code switch
```csharp
return fileInfo.Extension switch
{
    ".cs"  => await GetCodeDocumentsAsync(file, ct),   // → _codeParser.ParseAsync
    _      => await ParseFile(file, ct),               // → _codeParser.ParseAsync
};
```
Both branches invoke the **same** private method on the **same** parser instance. The entire factory adds zero behaviour. Any future developer will assume the branches do different things.

### 1.3 `NumberedRowDecorator.Render()` – non-idempotent mutation
`Render()` **adds** an index column and prepends row numbers to `inner.Table` on every call. A second call to `Render()` will add a *second* `#` column and duplicate every row. There is no guard against re-entry.

### 1.4 `ShowFileStage.EnumerateStoredFiles` – unguarded payload access
```csharp
var fileName = item.Payload[["FileName"]].StringValue;
```
If a point was written without a `"FileName"` key (schema drift, partial write), this throws a `KeyNotFoundException` with no context. There is also **no maximum-page guard** on the scroll loop, so a misbehaving Qdrant that always returns a non-null `NextPageOffset` would loop forever.

### 1.5 `QuestionCombineBuilder.GetCsvFilesAsync` – shared builder state
The injected `questionBuilder` is a **single shared instance**. The loop chains `WithText(...).WithFileName(...).SetCategory(...).SetActive(...)` and then calls `questionBuilder.Build()`. If `questionBuilder` holds internal mutable state (which the fluent API strongly implies), concurrent calls or a partially-chained failure can leak state into the next iteration or the next caller.

## 2. Architectural / Design Smells

### 2.1 Plugin loading pins the `Default` AssemblyLoadContext
```csharp
AssemblyLoadContext.Default.LoadFromAssemblyPath(dll);
```
The `Default` ALC is **never unloaded**. Every plugin DLL is held in memory for the lifetime of the process. There is no mechanism to hot-reload, version, or evict a plugin. This also means a single bad plugin DLL can crash the entire host.

### 2.2 `GeneratorExtensions.AsEmbeddingGenerator` – false abstraction
```csharp
public static IEmbeddingGenerator<string, Embedding<float>> AsEmbeddingGenerator(this IOllamaApiClient api)
{
    return api is IEmbeddingGenerator<string, Embedding<float>> generator
        ? generator
        : throw new InvalidCastException(...);
}
```
The method either returns the object unchanged or throws. It provides no conversion, no caching, no configuration. It is a cast with extra steps, and it creates a compile-time illusion that *any* `IOllamaApiClient` can be used where `IEmbeddingGenerator` is expected.

### 2.3 `FileDiscoveryService` – false async
```csharp
private async IAsyncEnumerable<string> GetValuesAsync(...)
{
    foreach (var path in ListFiles(directory, filter))  // synchronous I/O
    {
        cancellationToken.ThrowIfCancellationRequested();
        yield return path;
    }
}
```
`ListFiles` calls `Directory.EnumerateFiles` synchronously and enumerates the entire tree **before** any `yield return`. The `async` keyword and `CancellationToken` are decorative; the blocking work has already happened by the time the first item is consumed.

### 2.4 `QuestionFilterSelector` – static, hard-coded registry
```csharp
private static readonly ImmutableDictionary<QuestionCategory, IFilterStrategy> _strategies
    = ImmutableDictionary<...>.Empty.Add(QuestionCategory.XML, new XmlCommentFilterStrategy());
```
Adding a new category requires a code change in this one class. There is no DI, no plugin-discovery hook (ironic, given the codebase has a plugin system), and no way to override a strategy at runtime.

### 2.5 `FileConfigLoader` created inline, bypassing DI
```csharp
// QuestionCombineBuilder.GetFileConfig()
var fcl = new FileConfigLoader();
```
Every other dependency in the builder is injected. This one is `new`-ed, making it untestable without an `IFileConfigLoader` abstraction and preventing swap-ins for testing or alternative loaders.

### 2.6 Duplicated / conflicting `EmbeddingSetupExtension`
The file `EmbeddingSetupExtension.cs` appears **twice** in the codebase:
- Once as a bare `extension(IServiceCollection services)` block (C# 13 native extension).
- Once wrapped in `public static class EmbeddingSetupExtension` **containing** another `extension` block.

This is either a merge conflict, a copy-paste, or a migration in progress. At best it causes a compile-time ambiguity; at worst one is dead code.

## 3. Security / Operational Concerns

### 3.1 `Environment.UserName` written to logs
```csharp
// QuestionExecutionStage
logger.Information("Processing question [[...]] from user [[{UserId}]] ...", question.Text, Environment.UserName, ...);
```
In CI/CD, shared servers, or containerised deployments this leaks the OS account name. Prefer an application-level user identifier from configuration or claims.

### 3.2 `LoadQuestionPlugins` – broad exception swallowing
```csharp
catch (Exception ex)
{
    AnsiConsole.MarkupLine($"[[red]]Failed to load plugin: {dll}[[/]]");
    AnsiConsole.MarkupLine($"[[dim]]{ex.Message}[[/]]");
}
```
Catches *everything* (including `OutOfMemoryException`, `StackOverflowException`, `SecurityException`). `ReflectionTypeLoadException` (the common case for missing dependencies) is swallowed silently in terms of diagnostic depth — only `ex.Message` is shown, not the inner assembly/type that failed.

### 3.3 No path traversal guard on plugin loading
`LoadQuestionPlugins` enumerates `*.dll` under a well-known directory, but if an attacker can write to that path (shared volume, misconfigured permissions), they can inject arbitrary code into the process. There is no signature verification, hash check, or allow-list.

## 4. Maintainability / Code Hygiene

| Area | Issue |
|---|---|
| **C# version inconsistency** | Mixes C# 13 `extension` keyword, primary constructors, collection expressions (`[[]]`), and `required` members with more traditional patterns. Targeting different language versions across files makes the minimum SDK version ambiguous. |
| **XML doc CDATA corruption** | `CollectionInfo.cs`, `GeneratorExtensions.cs`, `CodeParserFactory.cs` all have malformed CDATA blocks (extra `[[`, missing `]]`), which will break doc generation (`csc /doc`) or produce broken output in Sandcastle/DocFX. |
| **`[[Required]]` + FluentValidation** | `FileLoadOptions` uses the .NET `[[Required]]` attribute *and* a separate `FileLoadOptionsValidator`. Two competing validation mechanisms for the same object create confusion about which is authoritative. |
| **`GenerationOptions.ThreadCount`** | Lives in a "Generation" options record but controls **embedding** concurrency. Misleading name will cause misconfiguration. |
| **`StageMetric` record** | Defined but never referenced by `PipelineRunner` or any stage. Dead code, or an abandoned feature. |
| **`OutputPathHelper.GetResponseDirectory`** | The `baseDir` parameter is ignored when `parts.Count > 0`, and used only when the collection is empty. The API contract is unintuitive and the two code paths produce different path shapes. |
| **`FilterBuilder.AddRange` ambiguity** | `AddRange("len", 50)` – is `50` the `gte` or the `lte`? The two-parameter overload is only documented for `lte`, but the three-parameter overload makes it `gte`. Easy to mis-call. |
| **No cancellation propagation in `QuestionCombineBuilder`** | `GetCategories()` and `GetFileConfig()` are synchronous; if they call I/O internally (file reads), there is no way to cancel them mid-enumeration. |
| **`PipelineRunner.ExecuteAsync` exception policy** | The `catch (Exception ex)` after the `OperationCanceledException` guard will also catch `OperationCanceledException` caused by a *timeout* (not the outer `ct`), wrapping it in a `PipelineStageException` and losing the timeout semantics. |

## 5. Testability Gaps

- **No test doubles visible.** `QuestionCombineBuilder` hard-codes `new FileConfigLoader()`. `QuestionExecutionStage` writes directly to a concrete `IOutputWriter` and a concrete `Serilog.ILogger` (which *is* an interface, but the `writer` coupling is tight).
- **`NumberedRowDecorator.Render()`** mutates state, making it impossible to unit-test in isolation without resetting the inner table.
- **`PipelineRunner`** uses a `Lock` (C# 13) which is a new API; test code on earlier runtimes will break.
- **`EmbeddingGeneratorService`** creates a `CancellationTokenSource` internally, making it hard to inject a fake timeout or observe the timeout path in tests.

## 6. Suggested Prioritisation

1. **Fix the timeout bug** (§1.1) – silent failures in production embedding calls.
2. **Remove the dead-code switch** in `CodeParserFactory` (§1.2) – eliminates a false architectural promise.
3. **Guard `NumberedRowDecorator.Render()`** against re-entry (§1.3).
4. **Add null/missing-key guards** in `ShowFileStage` and a max-page cap (§1.4).
5. **Make `questionBuilder` thread-safe or per-call** in `QuestionCombineBuilder` (§1.5).
6. **Migrate plugin loading** to a dedicated `AssemblyLoadContext` or at minimum add hash/signature verification (§2.1, §3.3).
7. **Resolve the duplicated `EmbeddingSetupExtension`** (§2.6) – one authoritative file.
8. **Inject `FileConfigLoader`** via DI (§2.5).
9. **Replace static `QuestionFilterSelector`** with DI-resolved `IFilterStrategy` collections (§2.4).
10. **Clean up XML docs, remove `[[Required]]` in favour of FluentValidation, rename `ThreadCount`** (§4).
11. **Add integration tests** for the pipeline runner, plugin loading, and embedding timeout paths (§5).

Each of the items above is individually addressable in a small PR; together they represent the bulk of the avoidable maintenance cost in this codebase.
