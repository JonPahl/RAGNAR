# Technical Debt Assessment – Ragnar RAG Application

## 1. Dead / Commented-Out Code

| Location | Issue |
|----------|-------|
| `NumberedRowDecorator.Render()` | ~20 lines of commented-out row-numbering logic. The method only adds a column header and delegates; the actual numbering never works. |
| `QuestionFilterSelector.FindFilter()` | Commented-out alternate return path left behind. |

| `RagnarConfigValidator` | `.OverrideChildRules()` is commented out, making the intent ambiguous. |

**Recommendation:** Delete the dead code or extract it into a dedicated integration test / feature-flag branch.

## 2. Single-Responsibility & Coupling Violations

- **`RagOrchestrator.ExecuteAsync`** builds the prompt string, calls the LLM, conditionally mutates the response by appending the prompt text, *and* persists the result — four distinct responsibilities in one method. The prompt-building logic (`$"Context:\n{contextText}…"`) is a magic-string template that should live in `IChatPromptProvider`.

- **`SummarizeSaveResponse`** derives the output directory from the *question's* file path (`Path.GetDirectoryName(details?.Question?.Filename)`). Output location is therefore coupled to input location, and the lazy `_responseDir ??= …` field is **not thread-safe** if the service is resolved as a singleton and called concurrently.

- **`CodeParserFactory`** dispatches on file extension but *both* branches call the same `_codeParser.ParseAsync`. The factory adds indirection with zero differentiation — it should either support a second parser or be inlined.

- **`QuestionCombineBuilder`** exposes both `GetCsvFilesAsync(string pluginDir, …)` and `GetCsvFileAsync(string csvFile, …)` whose bodies are ~90 % identical. The multi-file version could simply loop and call the single-file version.

## 3. Concurrency & Thread-Safety

| Risk | Detail |
|------|--------|
| `SummarizeSaveResponse._responseDir` | Mutable field with `??=` lazy init. If two questions for different source directories are processed in parallel, one call can overwrite the other's path. Use a `ConcurrentDictionary` or make the service scoped. |
| `PipelineRunner` | Uses `lock (_gate)` for stage mutation, but the retry policy is shared across all stages (`CachedPolicy`). A stage that is *not* retryable (e.g., `BrandingStage`) still gets 3 exponential-backoff retries on transient failures. |
| `FileDiscoveryService.ListFiles` | Calls `Directory.EnumerateFiles(rootPath, "*.*", SearchOption.AllDirectories)` which materialises the *entire* directory tree before the `Where` filter runs. For large repos this is a memory and I/O spike. Use `Directory.EnumerateFileSystemEntries` with lazy enumeration. |

## 4. Naming & Consistency

- **File ≠ Class:** `EmbeddingPointFactory.cs` contains `EmbeddingGeneratorService`. The file name misleads tooling and IDE navigation.
- **Duplicate registration entry points:** `EmbeddingSetupExtension` is defined *twice* — once as a top-level `extension(IServiceCollection)` block and once as a nested method inside a static class. Whichever the compiler resolves first is non-obvious.
- **Namespace qualification inconsistency:** `QuestionCombineBuilder.Build()` returns `IReadOnlyList<Core.Models.Question>` (fully qualified) while every other reference uses the unqualified `Question`.
- **Constant naming:** `AppDefaults.ORIGINAL_PROMPT_LABEL` is shown in the summary, but the actual field is `OriginalPromptLabel`. Documentation and code disagree.
- **`IFileValidator.IsValid`** accepts `in FileLoadOptions` (a by-ref parameter on a reference-type record). The `in` modifier is meaningless here and signals confusion with value types.

---

## 5. Error-Handling Gaps

- **`RagOrchestrator.ExecuteAsync`** never validates that `contextText` is non-empty. An empty retrieval result silently produces a low-quality LLM answer (or a model refusal) with no diagnostic.
- **`ApplicationConfigurationExtensions.LoadQuestionPlugins`** catches a bare `Exception`, prints via `AnsiConsole`, and continues. There is no structured logging, no correlation ID, and no way to surface plugin failures to the caller.
- **`PipelineRunner.ExecuteAsync`** catches `OperationCanceledException` *before* the generic `catch`, which is correct, but the generic branch wraps *any* exception (including `OperationCanceledException` from a child token that differs from `ct`) into `PipelineStageException`, masking cancellation.
- **`EmbeddingGeneratorService`** catches `TimeoutException` and logs `Fatal`, then *rethrows the same exception*. A `Fatal` log implies the process should stop, but it doesn't.

---

## 6. Security & Input Validation

- **`LoadQuestionPlugins`** calls `AssemblyLoadContext.Default.LoadFromAssemblyPath(dll)` on *every* `.dll` in a folder with no strong-name / signature verification. A malicious or corrupted DLL in `Questions/Plugins` would execute arbitrary code.
- **`SummarizeSaveResponse`** builds a file path from `details.Question.Filename` with no sanitisation. A question whose `Filename` contains `..\\..\\` or absolute-path segments could write outside the intended `Response/` directory (path-traversal).
- **`FilterBuilder`** and **`QuestionFilterSelector`** accept user-supplied filter values with no length or character-set validation before they are interpolated into Qdrant filter expressions.

---

## 7. Experimental / Forward-Looking C# Features

The codebase uses **C# 13 `extension` blocks** (`extension(IServiceCollection services)`, `extension(Assembly asm)`, `extension(QuestionBuilder builder)`) in at least four files. As of .NET 10 / C# 13 this is still an **experimental, preview feature**. Compiling against a stable SDK will fail. This creates a hard build dependency on a nightly / preview toolchain and prevents the project from being consumed by libraries targeting the stable language version.

Additionally, `required` members (C# 11), collection expressions `[[]]` (C# 12), and primary constructors (C# 12) are used throughout, so the minimum target is .NET 9+, but the `extension` keyword pushes it further.

## 8. Missing Cross-Cutting Concerns

| Concern | Gap |
|---------|-----|
| **Streaming** | LLM responses are generated fully in memory (`GenerateAsync` → `string`). For long answers this blocks the pipeline and prevents token-by-token console output. |
| **Circuit breaker** | There is a Polly retry on HTTP errors in `PipelineRunner`, but no circuit breaker. A down Ollama server will cause every stage to retry 3× before failing, multiplying latency. |
| **Health checks** | No `/health` endpoint or startup probe for the Ollama API or Qdrant collection. The pipeline will only discover unavailability at the first LLM call. |
| **Rate limiting / concurrency** | `GenerationOptions.ThreadCount` defaults to 8, but nothing enforces it. `QuestionExecutionStage` processes questions sequentially, so the setting is currently unused. |
| **Structured metrics** | `StageMetric` record exists but is never populated or exported (no OpenTelemetry, no Prometheus). |
| **Idempotency** | Re-running the pipeline over the same file set will duplicate Qdrant points and overwrite response Markdown files with no deduplication. |

---

## 9. Testability Smells

- `RagOrchestrator`'s private `GenerateAsync` and `SaveResponseAsync` methods are the only seams; they can't be unit-tested in isolation without invoking the full `ExecuteAsync` path.
- `QuestionCombineBuilder` and `PipelineRunner` are `sealed`, preventing test subclasses from overriding stage execution.
- `QuestionShowStage` takes **no** constructor parameters, while `QuestionExecutionStage` takes **five** — there's no consistent DI pattern across `IPipelineStage<T>` implementations, making it hard to write a shared test harness.
- The Ollama client is resolved via a factory (`IOllamaClientFactory.ResolveClient`) at call time rather than injected, making it harder to substitute a fake in tests.

## 10. Minor / Cosmetic Debt

- `QuestionShowStage.Name` returns `"Show Questions Stage"` but the XML doc says it returns `"Ask Questions Stage"` (copy-paste from `QuestionExecutionStage`).
- `BrandIngStage` (sic – check spelling in source) has no XML doc summary, unlike every other stage.
- `AssemblyExtensions.InformationalVersion` is a read-only property that calls `Resolve(asm)` every time; the doc says "cached" but no caching mechanism is visible.
- `AppDefaults` mixes PascalCase and ALL_CAPS naming conventions (`UnCategorizedCategory` vs `MarkdownFenceMarker`), which is inconsistent with C# `const` field guidelines.

## Suggested Prioritisation

1. **Fix the thread-unsafe `_responseDir`** (production data-corruption risk).
2. **Remove or gate the `extension`-block code** behind a `#if` so the project builds on a stable SDK.
3. **Eliminate the duplicated `EmbeddingSetupExtension`** and the duplicated CSV-loading methods.
4. **Add input validation / path sanitisation** to `SummarizeSaveResponse` and `LoadQuestionPlugins`.
5. **Split `RagOrchestrator.ExecuteAsync`** into prompt-building, generation, and persistence steps behind separate interfaces.
6. **Add a health-check / circuit-breaker** around the Ollama and Qdrant calls.
7. **Purge all commented-out code** and move the toast-notification experiment to a separate feature branch or integration test.
8. **Align naming** (file names, constant casing, return-type qualification) to reduce cognitive load.
