### 🔹 1. Pipeline / Chain of Responsibility
**Where it fits:** `FileParseFactory` → `EmbeddingPipeline` → `QdrantSearchService` → `SummaryAgent` → `ResponseWriter`  
**Why:** Your workflow is inherently sequential but currently coupled through direct DI or service calls. A pipeline pattern decouples stages, enables reordering, and makes testing/mocking each step trivial.

**Implementation Sketch:**
```csharp
public interface IPipelineStage<TIn, TOut>
{
    ValueTask<TOut> ExecuteAsync(TIn input, CancellationToken ct);
}

public class FileProcessingPipeline : IPipelineProcessor<RawFileContext, ProcessedResponse>
{
    private readonly IEnumerable<IPipelineStage<object, object>> _stages; // Typed via DI or registration

    public async ValueTask<ProcessedResponse> RunAsync(RawFileContext ctx, CancellationToken ct)
    {
        object? current = ctx;
        foreach (var stage in _stages)
            current = await ((dynamic)stage).ExecuteAsync((dynamic)current, ct);
        return (ProcessedResponse)current!;
    }
}
```
**Benefit:** Add/remove stages (e.g., `TokenizationStage`, `RateLimitStage`) without touching core logic. Aligns with your `EmbeddingPipeline` and `SummaryAgent` roles.

### 🔹 2. Decorator Pattern for Cross-Cutting Concerns
**Where it fits:** `IChatClient`, `IQdrantClient`, file I/O, or LLM response generation  
**Why:** You're calling external services (Ollama, Qdrant) that are prone to timeouts, rate limits, or transient failures. Decorators let you add retry, caching, timing, or logging without modifying core clients.

**Implementation Sketch:**
```csharp
public class RetryableChatClientDecorator : IChatClient
{
    private readonly IChatClient _inner;
    private readonly AsyncRetryPolicy _policy;

    public RetryableChatClientDecorator(IChatClient inner, IOptions<ResilienceOptions> opts)
    {
        _inner = inner;
        _policy = Policy.Handle<HttpRequestException>().WaitAndRetryAsync(3, i => TimeSpan.FromSeconds(Math.Pow(2, i)));
    }

    public async Task<string> GenerateAsync(string prompt, CancellationToken ct)
    {
        return await _policy.ExecuteAsync(async () => await _inner.GenerateAsync(prompt, ct));
    }
}
```
**Register in DI:** `services.Decorate<IChatClient, RetryableChatClientDecorator>();` (via Scrutor or Microsoft.Extensions.DependencyInjection.Abstractions extensions)

### 🔹 3. Specification Pattern for Complex Filtering
**Where it fits:** `FileLoadOptions.ExcludedDirectories`, `XmlEmptyCommentFilter`, question matching, vector search filters  
**Why:** Your current filtering uses hardcoded lists and simple conditions. Specifications make rules composable, testable, and configurable at runtime.

**Implementation Sketch:**
```csharp
public interface ISpecification<T>
{
    bool IsSatisfiedBy(T item);
}

public class FileLoadSpecification : ISpecification<string>
{
    private readonly ApplicationConfiguration _config;
    public FileLoadSpecification(IOptions<ApplicationConfiguration> config) => _config = config.Value.FileLoadOptions;

    public bool IsSatisfiedBy(string filePath)
    {
        var ext = Path.GetExtension(filePath);
        return _config.AllowedFileExtensions.Contains(ext, StringComparer.OrdinalIgnoreCase)
            && !_config.ExcludedDirectories.Any(dir => filePath.StartsWith(dir));
    }
}
```
**Benefit:** Swap or compose specifications dynamically. Pairs well with `IQuestionFactory` and `IFilterStrategy`.
