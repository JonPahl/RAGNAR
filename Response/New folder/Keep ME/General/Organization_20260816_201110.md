### 🔑 Key Organizational Principles Applied

| Group | Why It Belongs Here | Namespace Pattern |
|-------|---------------------|-------------------|
| `Ragnar.Core.Models` | Pure domain entities (`Question`, `CodeDocument`) with no external dependencies. | `Ragnar.Core.Models` |
| `Ragnar.Features.*` | Application use-cases & orchestration logic. Each feature owns its inputs, processing, and outputs. | `Ragnar.Features.{FeatureName}` |
| `Ragnar.Infrastructure.Ollama/Qdrant` | Third-party SDK wrappers, HTTP clients, and external service adapters. Easy to swap/mock later. | `Ragnar.Infrastructure.{Provider}` |
| `Ragnar.Shared.Extensions` | Static utility classes that don't belong to a specific feature. Prevents namespace pollution in domain/application layers. | `Ragnar.Shared.Extensions` |
| `Ragnar.Tests/*` | Mirrors production layout for predictable test discovery, mocking setup, and IDE navigation. | `Ragnar.Tests.{Layer}.{Feature}` |

### 🛠 Migration & Implementation Tips

1. **Namespace = Folder Path**: Always keep namespaces identical to the physical folder structure. This enables `dotnet new class -n MyClass -n MyProject.Features.Embeddings` tooling support and clean `using` statements.
2. **Move Extensions First**: Static extension classes (`StringExtensions`, `StopwatchExtensions`) should live in a dedicated `Shared.Extensions` project or folder to avoid circular dependencies when referenced across features.
3. **Keep `Point` with Qdrant**: Since `Point.FromFilePathAndIndex` is tightly coupled to Qdrant's ID generation strategy, it belongs in `Infrastructure/Qdrant`, not scattered in tests or core models.
4. **Test Structure**: Place each test class in a folder matching its production feature. Example: `RagOrchestratorTests.cs` → `tests/Ragnar.Tests/Features/RAGPipeline/`. This makes dependency mocking and setup highly localized.
5. **Avoid Deep Nesting**: If the project stays under ~15 files per feature, you can flatten to `src/Ragnar/Features/{Feature}/...` without a separate `Core` layer. Only split `Core` if models grow or become shared across multiple apps.

### ✅ Benefits of This Structure
- **High Cohesion**: All embedding-related code lives together; all file validation/parsing stays grouped.
- **Low Coupling**: Infrastructure adapters (`OllamaClientProvider`, `Qdrant`) are isolated, making them easy to mock in tests.
- **Scalable**: Adding a new feature (e.g., `Ragnar.Features.Analysis/`) follows the exact same pattern without refactoring existing code.
- **IDE Friendly**: IntelliSense, Go-to-Definition, and test discovery work predictably across large solutions.
