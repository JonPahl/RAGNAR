# Hot-Path Optimization Opportunities

After reviewing the codebase, I've identified several areas where `Span<T>`, `Memory<T>`, or parallelization could yield meaningful gains. I'll rank them by likely impact.

---

## 1. `VectorStoreRepository.UpsertBatchAsync` — Highest Impact

This is the most allocation-heavy hot path. Every batch iterates documents three times with intermediate collections:

```csharp
// Current: 3 allocations per batch (string list, point struct list, SelectMany expansion)
var texts = batch.Select(d => $"Context: {d.ElementName}\nCode:\n{d.Code}").ToList();
var points = batch.Select((d, idx) => generatorService.BuildPointStructs(d.AsPoint(), generated[[idx]].Vector.ToArray(), d))
                  .SelectMany(p => p).ToList();
```

**Concrete suggestions:**

- **Pre-size arrays with `Span<T>` / `ArrayPool<T>`:** Replace `.Select(...).ToList()` with a pre-allocated `T[[]]` and a simple `for` loop. This eliminates the LINQ iterator allocation *and* the `List<T>` growth.

```csharp
var texts = new string[[batch.Length]];
for (var i = 0; i < batch.Length; i++)
    texts[[i]] = string.Create(
        batch[[i]].ElementName.Length + batch[[i]].Code.Length + 28, // "Context: " + "\nCode:\n" + overhead
        (batch[[i]].ElementName, batch[[i]].Code),
        (pair, dst) =>
        {
            "Context: ".CopyTo(dst);
            pair.ElementName.AsSpan().CopyTo(dst[[dst.Length..]]);
            dst[[dst.Length..]] = "\nCode:\n";
            dst[[dst.Length..]] = pair.Code;
        });
```

- **Collapse `SelectMany` into a single pre-sized array:** Determine the total point count first (or assume a fixed points-per-document ratio), allocate one array, and fill it with index arithmetic instead of `SelectMany`.

- **Reuse the `List<(int, Exception)>` for `failed`:** It grows unboundedly on partial failures. Pre-allocate `new List<(int, Exception)>(batch.Length)` per batch iteration.

## 2. `ParsingStage.ExecuteAsync` — Parallelism Already Present, but Contention Is Visible

```csharp
var documents = new ConcurrentBag<CodeDocument>();
await Parallel.ForEachAsync(files, ..., async (filePath, token) =>
{
    var elements = await parseFactory.ParseAsync(filePath, token);
    foreach (var element in elements)
        documents.Add(element);   // ← CAS on the bag per element
    task.Increment(1);
});
```

**Concrete suggestions:**

- **Partition the bag per thread.** `ConcurrentBag.Add` is lock-free but still involves a thread-local + shared-list CAS. For a known `MaxDegreeOfParallelism`, allocate an array of per-thread `List<CodeDocument>` and concatenate once at the end:

```csharp
var partitioned = new List<CodeDocument>[[maxParallelism]];
for (var p = 0; p < maxParallelism; p++) partitioned[[p]] = [[]];

await Parallel.ForEachAsync(files, new ParallelOptions { CancellationToken = ct, MaxDegreeOfParallelism = maxParallelism },
    async (filePath, token) =>
{
    var elements = await parseFactory.ParseAsync(filePath, token);
    // Each task writes to a slot derived from its thread (or a local list)
});
context.Documents = [[..partitioned.SelectMany(l => l)]];
```

- **`Span<T>` in the parser itself** (not shown, but `IFileParseFactory.ParseAsync` presumably tokenises source). If it walks byte/char buffers, switching to `ReadOnlySpan<char>` or `Memory<char>` avoids the intermediate `string` copies that a typical `StreamReader` → `string[[]]` split would produce.

## 3. `StringExtensions` — `LastFolder` and `IsExcluded` Allocate Substrings

`CharacterCount` already uses `AsSpan()` (good), but the other two likely call `.Substring` / `.Contains` on `string`:

```csharp
// Hypothetical current implementation behind the property:
public string LastFolder => ... Path.TrimEndingDirectorySeparator(p).Split('\\','/').Last();
```

**Concrete suggestions:**

- **`LastFolder` via `Span<char>.LastIndexOf`:** No allocation, just find the last separator:

```csharp
public static ref readonly string LastFolder(this ReadOnlySpan<char> path)
{
    path = path.TrimEnd('\\', '/');
    var idx = path.LastIndexOfAny((char)92, (char)47); // backslash, forward slash
    return ref Unsafe.AsRef(path.Slice(idx + 1).ToString()); // or return a ref to the span
}
```

- **`IsExcluded` via `Span<char>.SequenceEqual` (case-insensitive):** Avoids the LINQ `Any` + `string.Equals` overhead per exclusion entry. For small exclusion lists this is marginal, but for 10+ entries it adds up across thousands of files in `ParsingStage`.

## 4. `OllamaEmbeddingService.CreateTimeoutCts` — Per-Call Allocation

```csharp
private CancellationTokenSource CreateTimeoutCts(CancellationToken parent)
{
    var cts = CancellationTokenSource.CreateLinkedTokenSource(parent);
    cts.CancelAfter(config.Value.EmbeddingOptions.Timeout);
    return cts;
}
```

This is called **per batch** inside `UpsertBatchAsync`. `CancellationTokenSource` allocation + registration/disposal of the linked token is non-trivial.

**Concrete suggestion:** If the timeout is fixed for the process lifetime (it comes from config), hoist a single `CancellationTokenSource` to the service level and use `CancellationTokenSource.CancelAfter` + `Reset` instead of creating/destroying one per call. Or, better yet, since `GenerateBatchAsync` is the only consumer, use the `HttpClient.Timeout` / `OllamaApiClient` built-in timeout mechanism and drop the manual CTS entirely.

## 5. `DataTableBuilder` — `ToArray()` per Row in `ToTable()`

```csharp
foreach (var row in _rows)
    table.AddRow(row.ToArray()); // allocates a new string[[]] per row
```

For a table with *N* rows this is *N* array allocations. If `Spectre.Console`'s `AddRow` accepts `IEnumerable<string>` (it does), you can pass the `List<string>` directly and skip the copy. If it truly requires an array, pre-allocate the arrays at `AddRow` time instead:

```csharp
public DataTableBuilder AddRow(params string[[]] cells)
{
    _rows.Add(cells); // store the params array directly — it's already a fresh array
    return this;
}
```

This is a micro-optimisation but removes one allocation per row in a method that's called in a tight loop when building summary tables.

## 6. `CsvFileQuestionProvider.LoadQuestionsAsync` — Projection Allocations

```csharp
return records.Select(r => new Question(r.IsEnabled, r.Text, r.FileName, r.Category));
```

If the upstream parser (`IRecordParser<QuestionRecord>`) yields a large enumerable, this forces materialisation of the full list of `Question` objects. If the consumer only iterates once, consider making `LoadQuestionsAsync` return an `IAsyncEnumerable<Question>` and doing the projection lazily, so the intermediate `QuestionRecord` list can be GC'd row-by-row instead of holding both lists in memory simultaneously.

## 7. `PipelineRunner.ExecuteAsync` — Inherently Sequential, but One Detail

Stages must run in order (each mutates `EmbeddingContext`), so you **cannot** parallelise the stage loop. However, the `for` loop body does:

```csharp
logger.Information("Starting stages [[{Index}/{Total}]]: {Name}", ...);
```

This is fine with Serilog's structured logging (no string interpolation), so there's no hidden allocation here. No change needed.

## 8. `File.ReadAllTextAsync` (first snippet) — I/O-Bound

```csharp
return await File.ReadAllTextAsync(filePath, cancellationToken);
```

This is a single large read into a `string`. `Memory<T>` won't help because `File.ReadAllTextAsync` is the terminal API. If the file is very large and you only need parts of it, switching to `FileStream` + `Memory<byte>` reads would let you process chunks without materialising the entire file. But for typical source files (< 1 MB) this is a non-issue.

## Summary Table

| Location | Technique | Expected Win |
|---|---|---|
| `VectorStoreRepository.UpsertBatchAsync` | `Span<T>` / `string.Create` / pre-sized arrays | **High** – eliminates 2–3 allocations × batch size |
| `ParsingStage` (ConcurrentBag) | Per-thread partitioned lists | **Medium** – removes CAS contention under high parallelism |
| `StringExtensions.LastFolder` | `Span<char>.LastIndexOf` | **Medium** – zero-allocation path for every file visited |
| `OllamaEmbeddingService.CreateTimeoutCts` | Hoist / reuse CTS, or use client-level timeout | **Low–Medium** – saves 1 alloc + 2 registrations per batch |
| `DataTableBuilder.ToTable` | Skip `ToArray()` copy | **Low** – *N* fewer allocations per table |
| `CsvFileQuestionProvider` | Lazy `IAsyncEnumerable` projection | **Low** – lower peak memory for large CSVs |

The single biggest lever is **item 1**: the embedding upsert loop runs once per batch of 32–64 documents and does three LINQ passes with intermediate heap allocations. Converting those to tight `for` loops over `Span<T>` / pre-sized arrays will cut per-batch allocation count roughly in half and reduce GC pressure in a long-running ingest pipeline.
