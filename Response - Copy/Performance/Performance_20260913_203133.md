# Performance Issues Identified

## 1. Quadratic-Time Batching in `VectorStoreRepository.UpsertBatchAsync`

**Problem:** `docs.Skip(i).Take(batchSize)` re-scans the list from the beginning on every iteration, making the total cost **O(n² / batchSize)**. For 10,000 documents with a batch size of 32, that's roughly 1.5 million element visits instead of 10,000.

```csharp
// ❌ Current — O(n²/batchSize)
for (var i = 0; i < docs.Count; i += batchSize)
{
    var batch = docs.Skip(i).Take(batchSize).ToList();
    // ...
}
```

**Fix:** Use a simple index slice or `Enumerable.Chunk`, both of which are **O(n)**:

```csharp
// ✅ Option A — indexed slice (no allocation beyond the batch itself)
for (var i = 0; i < docs.Count; i += batchSize)
{
    var batch = docs.GetRange(i, Math.Min(batchSize, docs.Count - i));
    // ...
}

// ✅ Option B — LINQ Chunk (clean, single pass)
foreach (var batch in docs.Chunk(batchSize))
{
    // batch is already a T[[]]; no extra .ToList() needed
    // ...
}
```

## 2. Sequential RAG Queries in `QuestionExecutionStage.ExecuteAsync`

**Problem:** Every question is processed strictly one-at-a-time. Each iteration issues a network call to the LLM (Ollama), which is **I/O-bound**. With 50 questions and a 3-second LLM latency, the stage takes ≥ 150 s wall-clock even though the CPU is idle waiting for responses.

```csharp
// ❌ Current — fully serial
foreach (var question in questions)
{
    // ...
    await ragOrchestrator.ExecuteAsync(question, contextText, cancellationToken).ConfigureAwait(false);
    // ...
}
```

**Fix:** Run the RAG calls concurrently with a bounded parallelism, then write results in order:

```csharp
// ✅ Parallel RAG with ordered output
var maxParallel = Math.Min(4, questions.Count);
var results = new (Core.Model.Question Question, Exception? Error)[[questions.Count]];

await Parallel.ForEachAsync(
    Enumerable.Range(0, questions.Count),
    new ParallelOptions { MaxDegreeOfParallelism = maxParallel, CancellationToken = cancellationToken },
    async (idx, token) =>
{
    try
    {
        await ragOrchestrator.ExecuteAsync(questions[[idx]], contextText, token).ConfigureAwait(false);
        results[[idx]] = (questions[[idx]], null);
    }
    catch (Exception ex) when (ex is not OperationCanceledException)
    {
        results[[idx]] = (questions[[idx]], ex);
    }
});

// Write output in original order
for (var i = 0; i < questions.Count; i++)
{
    writer.MarkupLine($"[[blue]]Question: {Markup.Escape(questions[[i]].Text)} [[/]]");
    writer.MarkupLine($"{i + 1} of {questions.Count}", Styles.Cyan);
}
```

> **Note:** If the LLM provider has rate limits, keep `maxParallel` low (2–4). The context retrieval (`GetContext`) is already done once outside the loop, which is correct.

## 3. Unnecessary `ToList()` Materialization in `UpsertBatchAsync`

**Problem:** `var docs = codeDocuments.ToList();` eagerly materialises the entire enumeration even if it's already a `List<T>`. For large document sets (thousands of code segments) this doubles peak memory.

```csharp
// ❌ Always copies
var docs = codeDocuments.ToList();
```

**Fix:** Check the type first; fall back to materialisation only when needed:

```csharp
// ✅ Avoid redundant copy
var docs = codeDocuments as List<CodeDocument> ?? codeDocuments.ToList();
```

## 4. Repeated String Allocation in the Per-Question Logging Loop

**Problem:** `contextText.Length.ToString("N0")` allocates a new string on **every** iteration, even though `contextText` never changes inside the loop.

```csharp
// ❌ Allocates each iteration
logger.Information("...{ContextLength} chars", question.Text,
    Environment.UserName, contextText.Length.ToString("N0"));
```

**Fix:** Hoist the invariant values before the loop:

```csharp
// ✅ Compute once
var contextLengthStr = contextText.Length.ToString("N0");
var userName = Environment.UserName;

foreach (var question in questions)
{
    logger.Information("...{ContextLength} chars",
        question.Text, userName, contextLengthStr);
    // ...
}
```

## 5. `ConcurrentBag` → Array Copy in `ParsingStage`

**Problem:** After parallel parsing, `context.Documents = [[..documents]];` forces a full copy from the `ConcurrentBag`'s internal linked structure. For very large document sets this is an extra O(n) allocation and enumeration of the bag's internal segments.

**Fix (minor):** If the count is known up front, pre-allocate an array and use an index-based writer to avoid the bag entirely:

```csharp
// ✅ Pre-sized array, no ConcurrentBag needed
var documents = new CodeDocument[[files.Count]]; // approximate; or use a growable buffer
var nextIndex = 0;
await Parallel.ForEachAsync(files, options, async (filePath, token) =>
{
    var elements = await parseFactory.ParseAsync(filePath, token).ConfigureAwait(false);
    var local = elements.ToArray();
    var start = Interlocked.Add(ref nextIndex, local.Length) - local.Length;
    Array.Copy(local, 0, documents, start, local.Length);
});
context.Documents = documents[[..nextIndex]];
```

For typical project sizes (hundreds of files) the `ConcurrentBag` cost is negligible, so this is a **low-priority** optimisation.

## 6. Repeated `Path.Join` / `Directory.CreateDirectory` in `ResponseWriter`

**Problem:** If many responses are written in a tight loop, `Directory.CreateDirectory(directory)` is called every time even though the directory already exists after the first call. On some filesystems this still incurs a syscall.

```csharp
// ❌ Called per response
public async Task<string> WriteResponseAsync(SaveDetails details, CancellationToken ct)
{
    var directory = pathResolver.ResolveResponseDirectory(details.Question.Category);
    Directory.CreateDirectory(directory);   // redundant after first call
    // ...
}
```

**Fix:** Track created directories in a `HashSet<string>` (or rely on the OS cache — on Linux/NTFS `CreateDirectory` on an existing dir is a cheap no-op, but on network filesystems it can be expensive):

```csharp
private readonly ConcurrentDictionary<string, byte> _createdDirs = new(StringComparer.OrdinalIgnoreCase);

public async Task<string> WriteResponseAsync(SaveDetails details, CancellationToken ct)
{
    var directory = pathResolver.ResolveResponseDirectory(details.Question.Category);
    _createdDirs.GetOrAdd(directory, d => { Directory.CreateDirectory(d); return 0; });
    // ...
}
```
