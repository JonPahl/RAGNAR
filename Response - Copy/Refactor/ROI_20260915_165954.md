# Top 3 Critical Technical Debt Items in Ragnar

## 1. No Resilience Layer for External Service Calls (Ollama + Qdrant)

**Impact: Critical | Remediation Effort: Medium**

The entire pipeline is a single point-of-failure chain: `OllamaEmbeddingService` → Qdrant upsert → Ollama LLM inference. Every one of these is a remote HTTP/gRPC call with **zero retry, circuit-breaker, or timeout-backoff logic**. A transient network blip, a brief Ollama model-load stall, or a Qdrant compaction pause aborts the *entire* multi-hundred-document embedding batch.

The tell: `appsettings.json` suppresses `Polly` warnings in Serilog (`"Polly": "Warning"`), indicating Polly was *planned* but never wired in. The `OllamaEmbeddingService` only applies a hard `CancelAfter` timeout — there's no retry, no exponential backoff, no fallback.

**Why it's #1:** In a RAG pipeline processing dozens of files, one 2-second network hiccup during a 30-second embedding call loses the whole batch. There is no partial-recovery path. In production, this is the single largest reliability risk.

**Remediation sketch:**
```csharp
// In DI registration (Program.cs / ServiceCollectionExtensions)
services.AddHttpClient(OllamaServiceType.Embedding, client =>
{
    client.BaseAddress = new Uri($"http://{opts.Host}:{opts.Port}");
    client.Timeout = opts.Timeout;
})
.ConfigurePrimaryHttpMessageHandler(() => new SocketsHttpHandler
{
    PooledConnectionLifetime = TimeSpan.FromMinutes(2),
})
.AddPolicyHandler(GetRetryPolicy())   // Polly: 3 retries, 2s → 4s → 8s, on 5xx/timeout
.AddPolicyHandler(GetCircuitBreakerPolicy()); // 5 failures in 30s → open 60s
```
Apply the same to the Qdrant gRPC client via a `CallInvoker` policy or a wrapper around `IQdrantClient`.

## 2. `VectorStoreRepository` Silently Discards Batch Failure Diagnostics

**Impact: High (operational blind spot) | Remediation Effort: Very Low**

```csharp
var failed = new List<(int Index, Exception Ex)>();
// …accumulates per-batch failures…
return new UpdateResult
{
    Status = failed.Count == 0 ? UpdateStatus.Completed : UpdateStatus.UnknownUpdateStatus
};
```

The `failed` list is **built, populated, and then thrown away**. The caller receives a binary enum with no count, no exception details, no index range. If 3 of 4 batches fail with `HttpRequestException`, the orchestrator logs "UnknownUpdateStatus" and has no way to know *which documents* are missing from the vector store, *why*, or whether a retry is safe.

This is particularly dangerous because the method **continues past failures** (the `catch` block intentionally does `continue`), so the pipeline appears to "succeed" while the knowledge base is silently incomplete.

**Why it's #2:** In a RAG system, missing embeddings mean the LLM answers from incomplete context — a *correctness* problem, not just an availability problem. And the operator has no signal to detect it.

**Remediation sketch (≈ 5 lines changed):**
```csharp
public async Task<UpdateResult> UpsertBatchAsync(…)
{
    // …existing loop…
    if (failed.Count > 0)
        logger.Error("Upsert completed with {Failed} failed item(s) across {Batches} batch(es). First error: {First}",
            failed.Count, batches.Count(), failed[[0]].Ex.Message);

    return new UpdateResult
    {
        Status   = failed.Count == 0 ? UpdateStatus.Completed : UpdateStatus.Partial,
        Succeeded = succeeded,
        Failed    = failed,          // expose the list
    };
}
```
Extend `UpdateResult` with `int Succeeded`, `int FailedCount`, and `IReadOnlyList<(int Index, string Error)>`. The data is already in scope; it just needs to leave the method.

## 3. `PathResolver` Couples Path Computation to Filesystem Existence

**Impact: Medium-High (crash on first run / clean CI) | Remediation Effort: Trivial (2 lines)**

```csharp
// PathResolver.cs
var responseDir = Path.Join(_applicationOptions.SourceDirectory, _applicationOptions.OutputFolder);
if (!Directory.Exists(responseDir))
    throw new DirectoryNotFoundException(responseDir);   // ← throws
return Path.Join(responseDir, baseDir);
```

```csharp
// ResponseWriter.cs
var directory = pathResolver.ResolveResponseDirectory(details.Question.Category);
Directory.CreateDirectory(directory);   // ← too late: the resolver already threw
```

The resolver is supposed to be a **pure path-computation** function, but it asserts a filesystem precondition. The writer that *creates* the directory never gets the chance because the resolver throws first. This means:

- **First run on a clean machine or CI agent** → `DirectoryNotFoundException` crash.
- **Any environment where `Response/` was cleaned between runs** → crash.
- The `PathResolver` is now **non-pure and non-deterministic** (same input, different result depending on disk state), which also makes it harder to unit-test in isolation.

**Remediation (delete 2 lines from `PathResolver`, add 1 to `ResponseWriter`):**

```csharp
// PathResolver.cs — remove the throw, keep the pure computation
public string ResolveResponseDirectory(QuestionCategory? category)
{
    var baseDir = category is null || string.IsNullOrWhiteSpace(category.ToString())
        ? nameof(QuestionCategory.Uncategorized)
        : category.ToString();
    return Path.Join(_applicationOptions.SourceDirectory,
                     _applicationOptions.OutputFolder,
                     baseDir);
}

// ResponseWriter.cs — ensure directory exists before writing (already partially does this)
public async Task<string> WriteResponseAsync(SaveDetails details, CancellationToken ct)
{
    var directory = pathResolver.ResolveResponseDirectory(details.Question.Category);
    Directory.CreateDirectory(directory);          // ← now actually reachable
    // …rest unchanged…
}
```
