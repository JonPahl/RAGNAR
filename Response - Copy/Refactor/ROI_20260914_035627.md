## 1. Broken Builder-Chain Semantics in `LoadQuestionsAsync` (Silent Data Corruption)

**Location:** `QuestionExecutionStage.LoadQuestionsAsync`

```csharp
// Current (buggy) code:
builder.GetCategories().GetFileConfig();            // ← intermediate result discarded
var pluginDir = Path.Join(AppContext.BaseDirectory, "Plugins");
await builder.GetCsvFilesAsync(pluginDir, cancellationToken).ConfigureAwait(false); // ← result discarded
builder.WithCategoryFilter();                       // ← result discarded
var sorted = builder.Build();
```

**Why it's critical:** Each builder call is treated as a fire-and-forget statement. This only works *by accident* if `IQuestionSourceAggregator` is self-referential (every method returns `this`). The moment any method returns a new instance carrying accumulated state, the `GetCategories()` and `GetFileConfig()` mutations are silently lost, and `Build()` produces an incomplete or empty question list. The application then proceeds to ask zero or wrong questions with no error surface.

**The test masks the bug:**
```csharp
_builderMock.Setup(b => b.GetCategories()).Returns(_builderMock.Object);
_builderMock.Setup(b => b.GetFileConfig()).Returns(_builderMock.Object);
// ...
_builderMock.Setup(b => b.Build()).Returns(questions);
```
Because every setup returns the *same* mock object, the test passes regardless of whether the real implementation is self-referential. It never verifies that state actually propagates through the chain.

**Remediation (low effort, ~15 min):**
```csharp
var sorted = await builder
    .GetCategories()
    .GetFileConfig()
    .GetCsvFilesAsync(pluginDir, cancellationToken)
    .ConfigureAwait(false);

sorted = (await sorted.WithCategoryFilter().ConfigureAwait(false)).Build();
```
Then add a test with a **non-self-referential** fake (each method returns a distinct object) to prove state actually flows.

**Impact:** HIGH — silently produces wrong or empty question sets in production.
**Effort:** LOW — code fix + one additional unit test.

## 2. `PathResolver` vs. `ResponseWriter` Existence-Check Conflict (First-Run Crash)

**Location:** `PathResolver.ResolveResponseDirectory` ↔ `ResponseWriter.WriteResponseAsync`

```csharp
// PathResolver — throws if the base response dir doesn't exist:
public string ResolveResponseDirectory(QuestionCategory? category)
{
    var responseDir = Path.Join(_applicationOptions.SourceDirectory, _applicationOptions.OutputFolder);
    if (!Directory.Exists(responseDir))
        throw new DirectoryNotFoundException(responseDir);  // ← explodes here
    return Path.Join(responseDir, baseDir);
}

// ResponseWriter — expects to create the category subfolder itself:
public async Task<string> WriteResponseAsync(SaveDetails details, CancellationToken cancellationToken)
{
    var directory = pathResolver.ResolveResponseDirectory(details.Question.Category); // ← throws first
    Directory.CreateDirectory(directory);  // ← never reached on a fresh install
    // ...
}
```

**Why it's critical:** On any fresh deployment, CI run, or new user machine where `Response/` has not been pre-created, the resolver throws `DirectoryNotFoundException` *before* the writer's `Directory.CreateDirectory` can execute. The entire "save response" path is dead on first run. Worse, the exception type (`DirectoryNotFoundException`) is misleading—it implies a filesystem issue rather than a bootstrap-ordering bug.

**Remediation (low effort, ~10 min):**
Move the creation responsibility into one place. Either:

```csharp
// Option A — PathResolver creates what it returns:
public string ResolveResponseDirectory(QuestionCategory? category)
{
    var baseDir = category?.ToString() ?? nameof(QuestionCategory.Uncategorized);
    var responseDir = Path.Join(_applicationOptions.SourceDirectory, _applicationOptions.OutputFolder);
    Directory.CreateDirectory(Path.Join(responseDir, baseDir));
    return Path.Join(responseDir, baseDir);
}
```
Then remove `Directory.CreateDirectory` from `ResponseWriter`. Or Option B: remove the existence check from the resolver entirely and let the writer own directory creation.

**Impact:** HIGH — hard crash, zero responses saved, user-visible exception.
**Effort:** LOW — two-line change + update one test.

## 3. `VectorStoreRepository` Opaque Batch-Failure Handling (Silent Data Loss)

**Location:** `VectorStoreRepository.UpsertBatchAsync`

```csharp
catch (Exception ex)
{
    logger.Error(ex, "Batch {Start}-{End} upsert failed.", i, i + batch.Count);
    failed.AddRange(batch.Select((d, idx) => (i + idx, ex)));
    // continue with next batch
}

// ...

return new UpdateResult
{
    Status = failed.Count == 0 ? UpdateStatus.Completed : UpdateStatus.UnknownUpdateStatus
    //         ↑ "everything fine"          ↑ "something went wrong (but what?)"
};
```

**Why it's critical (three compounding problems):**

| Problem | Consequence |
|---|---|
| `failed` list is populated but **never exposed** on `UpdateResult` | Callers cannot inspect *which* documents failed, *why*, or *how many* were lost |
| Status is `UnknownUpdateStatus` for any partial failure | A caller checking `result.Status == UpdateStatus.Completed` treats a 90 % loss the same as a clean abort |
| No retry or circuit-breaker around the per-batch `catch` | A transient Qdrant blip permanently loses that batch's vectors; the knowledge base is silently incomplete for all future RAG queries |

The net effect: after a partial upsert, the vector store is missing chunks. Every subsequent `IQuestionEmbedding.GetContext` call retrieves a **subset** of the corpus, degrading answer quality with no error signal anywhere in the pipeline.

**Remediation (medium effort, ~1–2 h):**
```csharp
public sealed record UpdateResult(
    UpdateStatus Status,
    int SucceededCount,
    int FailedCount,
    IReadOnlyList<(int Index, string Reason)> Failures)
{
    public static UpdateResult Success(int count)
        => new(UpdateStatus.Completed, count, 0, [[]]);

    public static UpdateResult Partial(int ok, int fail, IReadOnlyList<(int, string)> errs)
        => new(UpdateStatus.PartiallyCompleted, ok, fail, errs);
}
```
- Add `UpdateStatus.PartiallyCompleted` to the enum.
- Map each caught exception to `(index, ex.Message)` in the failures list.
- At the call site (`PipelineRunner` or the embedding stage), check `result.FailedCount > 0` and either re-queue the failed documents for a retry pass or surface a prominent warning to the console.
- Add a Polly `Retry` policy (2–3 attempts, exponential backoff) around the `qdrantClient.UpsertAsync` call to absorb transient gRPC errors before recording a permanent failure.

**Impact:** MEDIUM-HIGH — silent, cumulative degradation of RAG quality; hard to diagnose because no user-facing error is produced.
**Effort:** MEDIUM — new result type, retry policy, caller updates, and integration test that simulates a mid-batch gRPC failure.
