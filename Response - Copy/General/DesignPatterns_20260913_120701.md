# Design Pattern Recommendations for the Ragnar Codebase

## Patterns Already Well-Implemented

Before suggesting additions, it's worth acknowledging what's already solid:

| Pattern | Where |
|---|---|
| **Pipeline / Chain of Responsibility** | `PipelineRunner` → `IPipelineStage<EmbeddingContext>` |
| **Strategy** | `IFilterStrategy` / `XmlCommentFilterStrategy` |
| **Template Method** | `BaseFileParser` → abstract `ParseAsync` |
| **Factory** | `IOllamaClientFactory`, `IFileParseFactory` |
| **Builder** | `DataTableBuilder`, `IQuestionSourceAggregator` (fluent) |
| **Repository** | `VectorStoreRepository` |
| **Provider** | `CsvFileQuestionProvider`, `SummarizePromptProvider` |

That gives you a strong skeleton. The suggestions below fill the gaps.

## 1. Decorator – Cross-Cutting Stage Behaviour

**Problem.** `PipelineRunner` wraps every stage in a bare `try/catch`. Retry, circuit-breaking, timing, and structured-logging are all bolted on ad hoc. Adding a new cross-cutting concern (e.g., idempotency, audit logging) means editing the runner.

**Suggestion.**

```csharp
// Wraps any IPipelineStage with additional behaviour without touching the stage.
public sealed class RetryableStageDecorator(
    IPipelineStage<EmbeddingContext> inner,
    int maxAttempts,
    Serilog.ILogger logger) : IPipelineStage<EmbeddingContext>
{
    public string Name  => inner.Name;
    public bool ShouldRun => inner.ShouldRun;

    public async Task ExecuteAsync(EmbeddingContext ctx, CancellationToken ct)
    {
        for (var attempt = 1; ; attempt++)
        {
            try
            {
                await inner.ExecuteAsync(ctx, ct);
                return;
            }
            catch (OperationCanceledException) { throw; }
            catch (Exception ex) when (attempt < maxAttempts)
            {
                logger.Warning(ex, "Stage {Name} failed (attempt {A}/{M}), retrying…",
                    Name, attempt, maxAttempts);
                await Task.Delay(TimeSpan.FromSeconds(Math.Pow(2, attempt)), ct);
            }
        }
    }
}
```

Registration becomes composable:

```csharp
runner.AddStage(new RetryableStageDecorator(
    new ParsingStage(parseFactory, logger, writer),
    maxAttempts: 3,
    logger));
```

You can layer `CircuitBreakerDecorator`, `TimingDecorator`, `AuditDecorator`, etc. without modifying `PipelineRunner` or any stage.

## 2. Circuit Breaker – Resilient External Calls

**Problem.** `OllamaEmbeddingService` and `VectorStoreRepository` make HTTP/gRPC calls to Ollama and Qdrant. A downstream timeout or crash will hammer the dependency in a tight loop across batch iterations.

**Suggestion.** Introduce a small circuit-breaker abstraction (or use Polly) and wrap the external calls:

```csharp
public interface ICircuitBreaker
{
    Task<T> ExecuteAsync<T>(Func<CancellationToken, Task<T>> action, CancellationToken ct);
}
```

```csharp
// Inside VectorStoreRepository
var generated = await _breaker.ExecuteAsync(
    ct => embeddingService.GenerateBatchAsync(texts, ct), ct);
```

Benefits:
- Opens the circuit after *N* consecutive failures → fast-fails the remaining batches instead of waiting on every timeout.
- Half-open probing lets you detect recovery without a full restart.
- Works naturally with the batch loop you already have.

## 3. Specification – Composable Query Predicates

**Problem.** The filter system (`IFilterStrategy`, `Filter`, `Condition`, `FieldCondition`, `Range`, `Match`) is a one-off structure tied to the XML-comment use case. If a new question category needs a different rule (e.g., "C# files whose element name contains 'Repository' AND line count > 200"), you'd add yet another `IFilterStrategy` class.

**Suggestion.** Formalise into a **Specification pattern** with combinators:

```csharp
public interface ISpecification<T>
{
    bool IsSatisfiedBy(T candidate);
}

public sealed record AndSpec<T>(ISpecification<T> A, ISpecification<T> B) : ISpecification<T>
{
    public bool IsSatisfiedBy(T c) => A.IsSatisfiedBy(c) && B.IsSatisfiedBy(c);
}

public sealed record NotSpec<T>(ISpecification<T> Inner) : ISpecification<T>
{
    public bool IsSatisfiedBy(T c) => !Inner.IsSatisfiedBy(c);
}

public sealed record FieldRangeSpec<T>(Func<T, int> Selector, int? Lt, int? Gt) : ISpecification<T>
    // ...

public sealed record KeywordExclusionSpec<T>(Func<T, string> Selector, IEnumerable<string> Except) : ISpecification<T>
    // ...
```

Now `XmlCommentFilterStrategy` becomes a thin composition:

```csharp
ISpecification<CodeDocument> spec =
    new FieldRangeSpec<CodeDocument>(d => d.CommentLength, Lt: threshold)
 & new KeywordExclusionSpec<CodeDocument>(d => d.Category.ToString(),
        [["Test", "Tests", "Testing"]]);
```

This eliminates the parallel `Must` list-of-`Condition` tree and makes new rules declarative and unit-testable in isolation.

## 4. Mediator / Event Bus – Decoupling Stage Internals

**Problem.** `QuestionExecutionStage.ExecuteAsync` directly calls `writer`, `logger`, `questionEmbedding`, and `ragOrchestrator`. Any new consumer (metrics sink, UI progress bar, webhook) requires modifying the stage.

**Suggestion.** Define a lightweight domain-event bus:

```csharp
public record QuestionStarted(Question Q, string ContextLength);
public record QuestionCompleted(Question Q, int Index, int Total);
public record PipelineStageStarted(string StageName, int Index, int Total);
public record PipelineStageCompleted(string StageName, TimeSpan Elapsed);
```

```csharp
public interface IDomainEventBus
{
    void Publish<T>(T evt);
    IDisposable Subscribe<T>(Action<T> handler);
}
```

Stages **publish**; writers, loggers, and metrics **subscribe**. This keeps the "hot path" in the stage lean and lets you add a Seq sink, an in-progress Spectre table, or a webhook notifier without touching stage code.

## 5. Adapter – Pluggable Vector-Store Backends

**Problem.** `VectorStoreRepository` is hard-wired to `IQdrantClient`. The config exposes `VectorStoreName`, but switching to Weaviate, ChromaDB, or pgvector means forking the repository.

**Suggestion.**

```csharp
public interface IVectorStore
{
    Task<UpdateResult> UpsertAsync(string collection, IEnumerable<PointStruct> points, CancellationToken ct);
    Task<string>        SearchAsync(string collection, float[[]] vector, Filter? filter, int topK, CancellationToken ct);
    Task<bool>          CollectionExistsAsync(string name, CancellationToken ct);
}
```

```csharp
public sealed class QdrantVectorStore(IQdrantClient client) : IVectorStore { /* … */ }
public sealed class WeaviateVectorStore(WeaviateClient client) : IVectorStore { /* … */ }
public sealed class PgVectorStore(NpgsqlConnection conn) : IVectorStore { /* … */ }
```

`VectorStoreRepository` depends on `IVectorStore` instead of `IQdrantClient` directly. DI selects the concrete adapter from config.

## 6. Null Object – Eliminate Null-Checking Branches

**Problem.** `IQuestionProvider.LoadQuestionsAsync` can return empty collections; `GetContext` can return `""`. Callers must guard.

**Suggestion.**

```csharp
public sealed class NullQuestionProvider : IQuestionProvider
{
    public string ProviderName => "(none)";
    public Task<IEnumerable<Question>> LoadQuestionsAsync(string _, CancellationToken __)
        => Task.FromResult(Enumerable.Empty<Question>());
}
```

```csharp
public static class QuestionProviderExtensions
{
    public static IQuestionProvider OrNull(this IQuestionProvider? p) =>
        p ?? NullQuestionProvider.Instance;
}
```

The pipeline never sees a `null` provider; the empty path is handled uniformly.

## 7. Command – Unit of Work for the RAG Loop

**Problem.** `ragOrchestrator.ExecuteAsync(question, contextText, ct)` bundles embedding → retrieval → LLM call → response write into one opaque call. You can't retry *just* the write, skip the LLM for caching, or parallelise the retrieval.

**Suggestion.** Decompose into a small command chain (or a **Chain of Responsibility** over command handlers):

```csharp
public record RetrieveContextCommand(Question Q, string Collection) : IRagCommand;
public record GenerateAnswerCommand(Question Q, string Context)    : IRagCommand;
public record PersistResponseCommand(Question Q, string Answer)    : IRagCommand;

public interface IRagCommandHandler
{
    Task<IRagCommand?> HandleAsync(IRagCommand cmd, CancellationToken ct); // return next or null
}
```

Each handler is independently testable, retryable, and cacheable. The orchestrator simply walks the chain.

## 8. Caching with Invalidation – Context & Embedding Reuse

**Problem.** `questionEmbedding.GetContext(_collectionName, ct)` re-queries the vector store on every question. If multiple questions share the same source code base, the top-K context is largely the same. Embedding the *question* text is also repeated work if the same question text appears across CSV files.

**Suggestion.**

```csharp
public interface ISemanticCache
{
    Task<string>    GetOrAddAsync(string key, Func<CancellationToken, Task<string>> factory, CancellationToken ct);
    Task<float[[]]>   GetOrAddAsync(string key, Func<CancellationToken, Task<float[[]]>> factory, CancellationToken ct);
    void            Invalidate(string pattern);
}
```

Back it with a bounded `MemoryCache` (or Redis) with a TTL from `EmbeddingOptions.Timeout`. Invalidate when a new upsert batch completes.

## 9. Plugin Discovery – Formal Extension-Point Architecture

**Problem.** `QuestionExecutionStage` references a `Plugins/` directory, and the builder aggregates sources, but there's no formal discovery contract. Adding a new question source (e.g., Jira, Confluence) requires code changes.

**Suggestion.**

```csharp
public interface IPlugin
{
    string Name { get; }
    Task InitializeAsync(PluginContext ctx, CancellationToken ct);
}

public interface IQuestionSourcePlugin : IPlugin, IQuestionProvider { }
```

Use a simple reflection-based loader (or MEF / `Microsoft.Extensions.Hosting` plugin loading) that scans `Plugins/` for assemblies implementing `IQuestionSourcePlugin`. Register them in DI at startup. New sources ship as a DLL drop-in.

## 10. State Machine – Pipeline Lifecycle

**Problem.** `PipelineRunner` uses a flat `for` loop with a `ShouldRun` bool. There's no way to express "stage 3 can only run if stage 2 produced > 0 documents" or "if stage 4 fails, roll back stage 3's upserts."

**Suggestion.** Model the lifecycle with a lightweight state machine (or a **Saga** with compensation):

```csharp
public enum PipelineState { Idle, Discovering, Parsing, Embedding, Upserting, Questioning, Summarizing, Completed, Failed }

public interface ISagaStep
{
    PipelineState Target { get; }
    Task<PipelineState> ExecuteAsync(EmbeddingContext ctx, CancellationToken ct);
    Task CompensateAsync(EmbeddingContext ctx, CancellationToken ct); // rollback
}
```

The runner transitions states, and on failure walks backwards invoking `CompensateAsync`. This gives you transactional semantics across the batch upsert → question → summary flow.

## Summary – Priority Order

| # | Pattern | Impact | Effort |
|---|---------|--------|--------|
| 1 | **Decorator** (retry / timing / audit) | High – resilience, observability | Low |
| 2 | **Circuit Breaker** | High – prevents cascading failures | Low (Polly) |
| 3 | **Specification** (composable predicates) | Medium – extensibility of filters | Medium |
| 4 | **Mediator / Event Bus** | Medium – decoupling | Medium |
| 5 | **Adapter** (multi vector-store) | Medium – future-proofing | Medium |
| 6 | **Null Object** | Low – cleanliness | Low |
| 7 | **Command** (RAG decomposition) | Medium – testability, caching | Medium |
| 8 | **Caching** | Medium – latency, cost | Low |
| 9 | **Plugin Discovery** | Medium – extensibility | Medium |
| 10 | **State Machine / Saga** | High – correctness on failure | High |

Starting with **1 → 2 → 8** gives you the most resilience and performance gain for the least code change, and each subsequent pattern layers on top of those foundations without restructuring the pipeline you already have.
