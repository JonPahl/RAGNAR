### 1. RAG Pipeline Performs No Per-Question Vector Retrieval
**Impact: Critical · Effort: Medium-High**

`QuestionExecutionStage.ExecuteAsync` retrieves context **once** with no query vector, then feeds that same blob to every question:

```csharp
// QuestionExecutionStage.cs
var contextText = await questionEmbedding.RetrieveContextAsync(_collectionName, cancellationToken).ConfigureAwait(false);
foreach (var question in questions)
{
    // ← every question gets the identical contextText
    await ragOrchestrator.ExecuteAsync(question, contextText, cancellationToken).ConfigureAwait(false);
}
```

Compare this to the vector-search interface that *exists* but is never invoked in the hot path:

```csharp
// IVectorSearchService.cs – accepts a vector + filter per query
Task<string> RetrieveContextAsync(string collectionName, ReadOnlyMemory<float> vector, Filter? filter, CancellationToken cancellationToken);
```

`IContextRetriever` (used above) is a coarser interface that omits the vector parameter entirely. The consequence: the Qdrant collection, the embedding model (`nomic-embed-text`), and the filter strategies (`XmlCommentFilterStrategy`, etc.) are effectively dead infrastructure. Every question is answered from a single undifferentiated dump of stored text, which for a non-trivial repository will either exceed the LLM context window or drown the signal in noise. The application's stated purpose—"Repository Augmented Generator & Resolver"—is not actually realised.

**Remediation sketch**
1. In the loop, embed the question via the `Embedding` client (`factory.ResolveClient(OllamaServiceType.Embedding)`).
2. Call `IVectorSearchService.RetrieveContextAsync(collection, questionVector, question.Filter, ct)` per iteration.
3. Pass the question-specific `contextText` to the orchestrator.
4. Retire or re-scope `IContextRetriever` to a "full-collection dump" utility that is explicitly labelled as such.

### 2. Malformed Regex Patterns in `ApplicationOptionsValidator`
**Impact: High (config validation rejects valid input / accepts invalid) · Effort: Trivial**

```csharp
// ApplicationOptionsValidator.cs
private static readonly Regex _validFolderName = new(@"^[[[[\w.-]]]]+$", RegexOptions.Compiled);
// ...
.Matches(@"^[[[[a-zA-Z0-9_]]]]+$").WithMessage("VectorStoreName must be alphanumeric with underscores.");
```

In .NET regex the outermost `[[…` opens a character class; the second `[[` is a *literal* member. The first `]]` closes the class, so the trailing `]]+` requires one or more literal `]]` characters. The net effect:

| Intended pattern | Actual behaviour |
|---|---|
| `^[[\w.-]]+$` (word chars, dots, hyphens) | `^[[[[\w.-]]]]+$` → string must **end** with `]]+` |
| `^[[a-zA-Z0-9_]]+$` | `^[[[[a-zA-Z0-9_]]]]+$` → string must **end** with `]]+` |

A perfectly valid folder name like `Response` or `Ragnar` will **fail** validation because it does not end with `]]`. Any `IOptions`-level validation (`ValidateDataAnnotations` / `ValidateOnStart`) will therefore reject the application at startup unless those rules are bypassed.

**Fix (one line each):**

```csharp
private static readonly Regex _validFolderName = new(@"^[[\w.-]]+$", RegexOptions.Compiled);
// …
.Matches(@"^[[a-zA-Z0-9_]]+$")
```

### 3. `Dimension` Type Mismatch & Defeated Memory Semantics in the Embedding Path
**Impact: Medium (silent overflow / wasted allocation on every parse) · Effort: Low-Medium**

Two related issues compound in the parsing → embedding pipeline:

**a) `ulong → int` narrowing cast**

```csharp
// EmbeddingOptions.cs
public required ulong Dimension { get; init; }   // 64-bit

// FileParser.cs
var response = SplitMarkdown(filePath, fileContent.AsMemory(),
                             Convert.ToInt32(EmbeddingOption.Dimension), 50);
//                                    ^^^^^^^^^^^^^^^^^ potential OverflowException
```

`Convert.ToInt32` throws on values > `int.MaxValue`. A future model with a larger (or misconfigured) dimension would crash at parse time with an opaque `OverflowException` rather than a clear configuration error.

**b) Memory-to-string round-trip**

```csharp
// FileParser.cs
public override async Task<IEnumerable<CodeDocument>> ParseAsync(string filePath, CancellationToken cancellationToken)
{
    var fileContent = await ReadFileAsync(filePath, cancellationToken).ConfigureAwait(false); // string
    var response = SplitMarkdown(filePath, fileContent.AsMemory(), /*…*/);
    //                              ^^^^^^^^^^^^^^^^^^^^^^  string → ReadOnlyMemory<char>
    return [[.. response]];
}

private static List<string> LineSplit(in string content)   // ← back to string immediately
{
    var lines = new List<string>();
    lines.AddRange(content.Split(Environment.NewLine));
    return lines;
}
```

`SplitMarkdown` accepts `in ReadOnlyMemory<char>` to suggest zero-copy semantics, but `LineSplit` calls `.ToString()` on the very first use, materialising a full second copy of the file in memory. For multi-megabyte source trees this doubles peak allocation per file, and the `AsMemory()` call is pure overhead.

**Remediation**
- Change `Dimension` to `int` (or `int` with a `Guard`/range check in the validator—`OllamaOptionsValidator` already validates the port the same way).
- Either commit to memory semantics end-to-end (pass `ReadOnlyMemory<char>` into `LineSplit` and split on `'\n'` / `"\r\n"` without `ToString()`), or drop the memory indirection and work with `string` throughout to avoid the misleading API.
- Add a unit test asserting `Convert.ToInt32(ulong.MaxValue)` path throws a **config validation** error, not an `OverflowException` deep in the pipeline.
