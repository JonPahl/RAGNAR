### 🔴 Critical Issue: Thread-Safety Bug in `UpsertBatchAsync`
**Location**: `VectorStoreRepository.UpsertBatchAsync`
```csharp
await Parallel.ForEachAsync(tasks, ..., async (task, ct) => {
    ...
    embeddingGroup.Add(point); // ⚠️ List<T> is NOT thread-safe
});
```
**Problem**: `List<T>.Add` has no synchronization. Under concurrent execution, this will cause race conditions, data corruption, or `IndexOutOfRangeException`.
**Fix**: Use a thread-safe collection or collect sequentially after parallel work:
```csharp
var results = new ConcurrentBag<PointStruct>();

});

var points = results.ToArray(); // Materialize once for UPSERT
```

### 🟠 High-Impact Optimizations (Allocations & `Span<T>`/`Memory<T>`)

#### 1. Quadratic String Allocation in `OllamaChatResponse.GenerateResponse`
**Location**: Streaming token accumulation
```csharp
completeText += Markup.Escape(msg); // ⚠️ O(n²) string concatenation
```
**Problem**: Every `+=` on a `string` allocates a new array. For long LLM responses, this causes heavy GC pressure and latency spikes.
**Fix**: Use `StringBuilder` or `ArrayPool<char>`:
```csharp
var sb = new StringBuilder(capacity: 4096); // Pre-allocate based on expected response size
await foreach (var token in _ollamaClient.ChatAsync(ChatRequest, Ct))
{
    var escaped = Markup.Escape(token.Message.Content);
    sb.Append(escaped);
    responseMarkup = new Markup(sb.ToString(), Styles.Yellow); // Or update chunk-wise if UI supports it
    ctx.Refresh();
}
return sb.ToString();
```

#### 2. String Interpolation & File Content Assembly in `LoadFolderContentsAsync`
**Location**: `SummaryAgent.LoadFolderContentsAsync`
```csharp

return $"{AppDefaults.CODE_BLOCK_START} {builder} {AppDefaults.FILEMARKEREND}\n{text}\n"; // ⚠️ Multiple allocations
```

```csharp
char[[]] sharedBuffer = pool.Rent(1 << 20); // 1MB pooled buffer

int offset = 0;

foreach (var file in files)
{
    var fileName = Path.GetFileName(file);
    var header = $"---\n{AppDefaults.FILE_MARKER_START}{fileName}{AppDefaults.FILEMARKEREND}\n";
    // Write header to span...
    // Read file directly into span or small buffers...
    offset += text.Length;
}

var result = new string(span.Slice(0, offset));
pool.Return(sharedBuffer);
return $"{AppDefaults.CODE_BLOCK_START} {result} {AppDefaults.FILEMARKEREND}";
```
*Note*: If files are extremely large, consider streaming directly to a `MemoryStream` or using `System.IO.Pipelines` for zero-copy parsing.

### 🟡 Parallelization & I/O Improvements

#### 1. `LoadFolderContentsAsync` is Sequentially Reading Files
**Problem**: File I/O is bound to disk/network latency, not CPU. Running sequentially underutilizes cores.
**Fix**: Parallelize safely by collecting strings first, then joining:
```csharp
var fileTasks = files.Select(async f => 
{
    var content = await File.ReadAllTextAsync(f, Ct);
    return $"---\n{AppDefaults.FILE_MARKER_START}{Path.GetFileName(f)}{AppDefaults.FILEMARKEREND}\n{content}\n";
});

var contents = await Task.WhenAll(fileTasks);
return $"{AppDefaults.CODE_BLOCK_START} {string.Concat(contents)} {AppDefaults.FILEMARKEREND}";
```
*Note*: `string.Concat` is highly optimized and avoids intermediate allocations.

#### 2. Parallelism Degree in `UpsertBatchAsync`
**Current**: `MaxDegreeOfParallelism = 4`
**Problem**: Embedding generation (via Ollama) is likely CPU/GPU-bound, but HTTP requests are I/O-bound. Hardcoding `4` may throttle throughput on modern machines.
**Fix**: Use dynamic concurrency or rely on async I/O parallelism:
```csharp
// For I/O bound work, higher concurrency often helps. 
// Or simply use Task.WhenAll if embeddings don't block the thread pool heavily:
var embeddingTasks = CodeDocuments.Select(doc => GenerateEmbeddingAsync(...));
var results = await Task.WhenAll(embeddingTasks);
```
