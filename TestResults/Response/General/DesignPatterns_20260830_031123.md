### 🔹 1. Pipeline / Orchestrator Pattern (MediatR or Custom Workflow)
**Where it applies**: `SummaryAgent`, `VectorStoreRepository`, `ResponseWriter`, `FileWriter`
**Why**: Your app follows a clear multi-step workflow: `Load Files → Generate Embeddings → Upsert to Qdrant → Query LLM → Format & Write Response`. Currently, orchestration logic is scattered across classes with tight coupling.
**How to apply**:
- Introduce an `ICodeAnalysisPipeline` interface with stages like `IFileLoaderStage`, `IEmbeddingStage`, `IQueryStage`, `IResponseWriterStage`.
- Use **MediatR** (`IPipelineBehavior`) or a lightweight state machine to chain these steps. Each stage receives context via a shared `AnalysisContext` DTO.
```csharp
public class CodeAnalysisPipeline : ICodeAnalysisPipeline {
    public async Task<AnalysisResult> ExecuteAsync(AnalysisRequest request, CancellationToken ct) {
        var loaded = await _fileLoader.LoadAsync(request.SourceDir, ct);
        var embeddings = await _embeddingService.GenerateBatchAsync(loaded, ct);
        var upserted = await _repository.UpsertBatchAsync(embeddings, ct);
        var response = await _agent.QueryAsync(upserted.Context, request.Question, ct);
        return await _writer.WriteResponseAsync(response, ct);
    }
}
```
**Benefit**: Decouples lifecycle steps, enables individual stage testing, and makes the flow explicit and configurable.

### 🔹 2. Observer Pattern + `IProgress<T>` (Decouple Streaming from UI)
**Where it applies**: `OllamaChatResponse` (mixes streaming data with Spectre.Console rendering)
**Why**: The class violates SRP by embedding `AnsiConsole.Live`, `Markup`, and spinner logic directly in the business flow. This makes headless mode, testing, or alternative UIs impossible.
**How to apply**:
- Emit tokens via `IProgress<string>` or `IObservable<string>`.
- Create a separate `IConsoleRenderer` that subscribes to the stream and updates the UI.
```csharp
public interface IStreamingResponse {
    IObservable<string> TokenStream { get; }
    Task<string> FinalizeAsync(CancellationToken ct);
}

public class OllamaStreamingService : IStreamingResponse {
    public async Task SubscribeAsync(IProgress<string> progress, CancellationToken ct) { ... }
}
```
**Benefit**: Pure data stream vs. presentation layer separation. Enables CLI, Web, and Desktop clients to reuse the same core logic.

### 🔹 3. Immutable Request & Builder Patterns (Fix Concurrency Bugs)
**Where it applies**: `SummarizePromptProvider.Content` (mutable property), `SummaryAgent.Prompt`, `QdrantVectorStoreBuilder`
**Why**: `Content { get; set; } = string.Empty;` in a DI-registered class will cause race conditions if multiple requests hit the same instance concurrently.
**How to apply**:
- Replace mutable providers with **Immutable Request DTOs** or **Builder Pattern**.
- Pass context explicitly per invocation:
```csharp
public record SummarizeRequest(string Folder, string Question, IReadOnlyList<string> FileContents);

public class SummaryAgent {
    public async Task<string> SummarizeAsync(SummarizeRequest request, CancellationToken ct) {
        var prompt = PromptBuilder.BuildSummaryTemplate(request.FileContents);
        // ... generate response
    }
}
```
**Benefit**: Thread-safe DI registration, explicit data flow, easier mocking/testing.

### 🔹 4. Abstract Factory Pattern (Enhance Existing Client Factory)
**Where it applies**: `IOllamaClientFactory`, `OllamaEmbeddingService`, `OllamaChatResponse`
**Why**: You already have a factory, but client creation logic is duplicated (`FindClient(OllamaServiceType.Ollama)` appears in multiple places). If you later support cloud APIs or different embedding backends, this will become messy.
**How to apply**:
- Define an `IClientFactory` that returns families of related objects:
```csharp
public interface IClientFactory {
    IChatClient CreateChatClient();
    IEmbeddingGenerator<string, Embedding<float>> CreateEmbeddingGenerator();
}

public class OllamaClientFactory : IClientFactory { ... }
public class OpenAIClientFactory : IClientFactory { ... }
```
- Register via DI with `KeyedServices` or environment-based resolution.
**Benefit**: Centralized lifecycle management, easy backend swapping, cleaner constructor signatures.

### 🔹 5. Template Method Pattern (Standardize Prompt Generation)
**Where it applies**: `SummarizePromptProvider`, `CsvFileQuestionProvider`, `XmlCommentFilterStrategy`
**Why**: These classes share a common skeleton: `Validate → Assemble Context → Format Template → Return`. Divergence leads to inconsistent prompt structures and validation gaps.
**How to apply**:
```csharp
public abstract class BasePromptTemplate {
    protected abstract string CoreTemplate { get; }
    protected abstract void ValidateContext();
    
    public string Build(object context) {
        ValidateContext();
        var filled = FillTemplate(CoreTemplate, context);
        return PostProcess(filled);
    }
}

public class SummaryPromptTemplate : BasePromptTemplate { ... }
public class QuestionPromptTemplate : BasePromptTemplate { ... }
```
**Benefit**: Enforces consistent prompt assembly, centralizes validation/formatting, reduces boilerplate.

### 🔹 6. Facade Pattern (Simplify Complex Subsystems)
**Where it applies**: `RagnarConfig`, Qdrant setup, Ollama clients, file I/O, console rendering
**Why**: Consumers must juggle configuration, vector store initialization, embedding generation, and response writing. A single entry point would drastically reduce client complexity.
**How to apply**:
```csharp
public interface IRagnarOrchestrator {
    Task<AnalysisResult> AnalyzeAsync(AnalyzeOptions options, CancellationToken ct);
}

public class RagnarFacade : IRagnarOrchestrator { ... }
```
**Benefit**: Hides internal complexity, provides a clean public API, aligns with Clean Architecture boundaries.
